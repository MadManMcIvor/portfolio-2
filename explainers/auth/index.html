Who are you, and what are you allowed to do?

Every login screen, API key and “Sign in with Google” button is answering one of those two questions. This is a field guide to how they do it, and to the cryptography that makes the answers trustworthy.

Foundations

The two questions

Authentication (AuthN) establishes identity. Authorization (AuthZ) decides what that identity can do. They’re separate steps, and confusing them is the root of a lot of bugs.

Think of an airport. Showing your passport at security is authentication: someone checks that you are who you claim to be. Your boarding pass is authorization: it says which flight you may board and which lounge you can enter. A valid passport doesn’t get you onto every plane.

Authentication always comes first, and it usually produces some kind of credential you carry afterwards, such as a session cookie or a token, so you don’t have to show your passport at every gate. Authorization is then checked on every request, using that credential to look up who you are.

The status codes are misnamed

HTTP 401 Unauthorized actually means unauthenticated: “I don’t know who you are, please log in.” 403 Forbidden means “I know who you are, and you’re not allowed.” Returning the right one helps clients react correctly (redirect to login versus show an error).

The vocabulary you’ll see everywhere

  • Principal: the thing being authenticated. A user, a service, a device.
  • Credential: what the principal presents as proof. A password, a key, a certificate, a token.
  • Factor: a category of proof. Something you know (password), have (phone, security key) or are (fingerprint).
  • Identity provider (IdP): a system whose job is authenticating people and vouching for them to other apps. Google, Okta, Microsoft Entra ID, Auth0.

Encoding, hashing, encryption

Four tools that look similar in a hex dump but do completely different jobs. Mixing them up is the most common auth mistake.

Encoding

Reformats data so it travels safely (Base64, URL encoding). Anyone can reverse it.

Provides zero secrecy.

Hashing

A one-way fingerprint of fixed length (SHA-256). Same input, same output; you can’t go backwards.

Integrity checks, password storage.

Encryption

Scrambles data so only someone with the key can unscramble it (AES, RSA).

Confidentiality.

Signing

Attaches proof of who produced the data and that it hasn’t changed (HMAC, RSA, ECDSA).

Authenticity and integrity, not secrecy.

Try it: the same input, three ways

Type anything. Notice that Base64 is obviously reversible, a single character change scrambles the whole SHA-256 hash, and the HMAC changes again because it mixes in a secret key the server holds.

Symmetric versus asymmetric

Symmetric cryptography uses one shared secret for both directions. AES encrypts and decrypts with the same key; HMAC signs and verifies with the same key. It’s fast, but both sides must already share the secret, and anyone who can verify can also forge.

Asymmetric (public-key) cryptography uses a mathematically linked pair: a private key you never share and a public key you can hand to anyone. It’s slower, but it solves the “how do we share a secret with a stranger” problem. RSA and elliptic-curve algorithms (ECDSA, Ed25519, ECDH) are the common families.

Real systems combine both: asymmetric crypto to authenticate and agree on a key, then symmetric crypto for the bulk of the data. TLS works exactly this way.

Public and private keys

The pair does two different things depending on which key you start with.

GoalYou useThey useWhat it proves
Encrypt a message to someoneTheir public keyTheir private key to decryptOnly the key owner can read it
Sign somethingYour private keyYour public key to verifyYou produced it, and it wasn’t changed

A useful image: the public key is an open padlock you hand out freely. Anyone can snap it shut on a box (encrypt), but only your private key opens it. Signing runs the other way: you press a seal only you own into wax, and anyone holding a picture of your seal (the public key) can confirm it’s genuine.

In auth, signing is the workhorse. An identity provider signs tokens with its private key and publishes its public keys (often at a JWKS URL) so any app can verify those tokens without ever being able to mint one. Passkeys, SSH keys, SAML assertions and TLS certificates all rest on signatures.

Signed is not secret

A signature proves origin and integrity. It doesn’t hide anything. A signed JWT is readable by anyone who holds it.

TLS and HTTPS

Almost every auth method on this page assumes the connection is already encrypted. TLS is what makes that true.

When your browser connects, the server presents a certificate: its public key plus a statement, signed by a certificate authority (CA), that the key belongs to that domain. Your browser trusts a built-in list of CAs, so it can verify the chain. Then both sides run an ephemeral key exchange (ECDHE) to derive shared symmetric keys, and the rest of the conversation is encrypted with those.

TLS normally authenticates only the server. The client still has to prove who it is with one of the methods below, unless you use mutual TLS.

Storing passwords

Never store passwords, and never encrypt them. Store a slow, salted hash.

If passwords are encrypted, whoever gets the key gets every password. If they’re hashed with a fast algorithm like SHA-256, an attacker with a GPU can try billions of guesses per second against a stolen database. Password hashing algorithms are deliberately slow and memory-hungry to make each guess expensive.

  • Use Argon2id (the current recommendation), scrypt, or bcrypt. Use your language’s well-maintained library; don’t implement these yourself.
  • Salt: a random value unique to each user, stored beside the hash. It ensures two people with the same password get different hashes and defeats precomputed lookup tables. Modern libraries handle salting for you.
  • Pepper (optional): an extra secret kept outside the database, so a database leak alone isn’t enough.

# Login check (pseudocode)
user = db.find(email)

    start_session(user)
Good practice

Return the same generic message (“Email or password is incorrect”) whether the account exists or not, rate-limit login attempts, and check new passwords against known-breached lists.

Proving who you are

Basic auth

Send the username and password with every single request, Base64-encoded in a header.

# "ada:s3cret" in Base64
GET /reports HTTP/1.1
Host: api.example.com
Authorization: Basic YWRhOnMzY3JldA==

Good for internal tools, scripts, quick prototypes and some machine-to-machine APIs. It’s built into every HTTP client and needs no extra infrastructure.

Weaknesses: the real password crosses the wire constantly; there’s no clean logout (browsers cache the credentials); no MFA; no expiry; and the server must run a slow password hash on every request.

Base64 is not encryption

Anyone who sees that header can decode it in a second. Basic auth is only acceptable over HTTPS.

A cousin, Digest auth, hashes the credentials with a server challenge. It’s rarely used now, because HTTPS plus Basic is simpler and better.

API keys

A long random string that identifies an application or account, sent with each request.

GET /v1/forecast?city=sacramento HTTP/1.1
Authorization: Bearer sk_live_51Hx...k9Q
# or, by convention on some APIs
X-API-Key: sk_live_51Hx...k9Q

API keys are effectively long-lived passwords for software. They usually identify a project or account rather than an individual person, which makes them ideal for developer-facing APIs, billing and rate limiting, and a poor fit for “act on behalf of this user.” For that, use OAuth.

  • Send them in a header, not the URL. URLs end up in logs, browser history and analytics.
  • Store only a hash of the key on the server, like a password. Show the full key to the user once.
  • Give keys scopes (read-only, specific resources), expiry and easy rotation. Prefixes like sk_live_ help secret scanners catch leaks.
  • Never ship a secret key inside a mobile app or browser JavaScript. Anything on the client is public.

Sessions and cookies

Log in once, and the server remembers you. The browser holds only a random ticket number; the server holds what it means.

This is the classic, battle-tested approach for websites. Because the session lives on the server, you can revoke it instantly (logout, “sign out of all devices,” banning a user). The trade-off is that every server needs access to the session store, which usually means Redis or a database once you have more than one server.

Cookies are just a transport

A cookie is a small value the browser stores per site and attaches automatically to matching requests. It can hold a session ID, a JWT, or anything else. Its attributes are where the security lives:

Set-Cookie: __Host-sid=abc123; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=28800
AttributeWhat it does
HttpOnlyJavaScript can’t read the cookie, so an XSS bug can’t steal it directly.
SecureOnly sent over HTTPS.
SameSiteStrict: never sent on cross-site requests. Lax: sent on top-level navigations (clicking a link) but not on cross-site form posts or fetches; most browsers default to this. None: always sent; requires Secure. This is your main CSRF defense.
DomainWhich hosts receive it. Omit it to lock the cookie to the exact host; setting it widens it to subdomains.
PathWhich URL paths receive it.
Max-Age / ExpiresWhen it dies. Without either, it’s a “session cookie” that ends when the browser closes (though browsers that restore tabs may keep it).
__Host- prefixBrowser enforces Secure, Path=/ and no Domain, preventing subdomains from overwriting it.
Good practice

Generate a fresh session ID at login (prevents session fixation), use long cryptographically random IDs, set an idle timeout and an absolute timeout, and delete the server record on logout.

Tokens and JWT

Instead of a pointer to server data, hand the client a signed note that carries the data itself.

A bearer token is any credential where possession equals access, like cash: whoever bears it can use it. It’s sent in a header:

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOi...

A token can be opaque (a random string the server looks up, much like a session ID) or self-contained. A JSON Web Token (JWT, said “jot”) is the common self-contained format: three Base64URL-encoded parts joined by dots.

  1. Header: which algorithm signed it, and often a kid (key ID) saying which key.
  2. Payload: the claims, which are facts about the subject and the token.
  3. Signature: computed over the first two parts. Change one byte and verification fails.

HS256 versus RS256 / ES256

      
HS256 uses HMAC with one shared secret. Anything that can verify can also forge, so it only suits a single service signing tokens for itself. RS256 (RSA) and ES256 (ECDSA) sign with a private key and verify with a public key, so the auth server signs and many APIs verify safely. Public keys are typically published at a /.well-known/jwks.json URL and matched by kid.

      
Access and refresh tokens

      
Since a self-contained JWT is valid until it expires, and you can’t easily un-issue it, keep access tokens short-lived (5 to 15 minutes). Pair them with a longer-lived refresh token, stored more carefully, that the client trades for new access tokens. Rotate refresh tokens on each use so a stolen one is detectable.

      
      

        
Sessions
Easy to revoke, small cookie, server holds the truth.
Needs a shared store across servers.

        
JWTs
Stateless verification, works across services and domains.
Hard to revoke, larger, easy to misuse.

      

      
JWT pitfalls
Always verify the signature with an algorithm you choose, never the one the token’s header claims (this blocks alg: none and key-confusion attacks). Check exp, iss and aud. Don’t put secrets or sensitive personal data in the payload; it’s only encoded. If you need the contents hidden, that’s JWE, a different format.

    


    

      
Where to keep tokens

      
There’s no perfect spot in a browser. Each option trades one attack for another.

localStorageYesNoUntil cleared, shared by all tabsAny XSS can read and exfiltrate it

          
sessionStorageYesNoOne tab, gone when it closesSame XSS risk, slightly smaller window

          
JS memory (a variable)Only your codeNoLost on refreshXSS can still use it while the page is open

          
Native Keychain / KeystoreApp onlyNoPersistentDevice compromise

        
      

      
The two attacks behind the trade-off

      
XSS (cross-site scripting): an attacker gets their JavaScript running on your page. It can read anything JavaScript can read, including localStorage, sessionStorage and non-HttpOnly cookies. Defenses: output escaping, a Content Security Policy, and keeping tokens out of JS reach.

      
CSRF (cross-site request forgery): a malicious site makes the victim’s browser send a request to your site, and the browser helpfully attaches your cookies. Defenses: SameSite=Lax or Strict, anti-CSRF tokens on state-changing requests, and checking the Origin header.

      
The usual recommendation
For browser apps, keep credentials in HttpOnly; Secure; SameSite cookies. If a single-page app needs OAuth tokens, a “backend for frontend” (BFF) holds them server-side and gives the browser only a session cookie. Avoid putting long-lived tokens in localStorage.

    


    

      
MFA and passkeys

      
Passwords leak and get phished. A second factor, or no password at all, closes most of that gap.

      

        
MethodHow it worksPhishing-resistant?

        
          
SMS / email codesA code is sent to youNo. Vulnerable to SIM swaps and fake login pages

          
TOTP appsApp and server share a secret; both compute HMAC(secret, current 30-second window) into a 6-digit codeNo. Codes can be relayed by a fake site

          
Push approvalTap “Approve” on your phonePartly. Prone to “MFA fatigue” spam; number matching helps

          
Security keys / passkeys (WebAuthn)Public-key signature bound to the site’s originYes

        
      

      
Passkeys (WebAuthn / FIDO2)

      
At registration, your device creates a key pair just for that website and sends the server only the public key. At login, the server sends a random challenge; your device asks for your fingerprint, face or PIN, then signs the challenge with the private key. The browser includes the site’s origin in what gets signed, so a look-alike phishing domain gets a signature that’s useless on the real site.

      
      
Passkeys can sync across a person’s devices through their platform (Apple, Google, Microsoft, or a password manager), while hardware security keys keep the private key on one physical device.

    


    

      
Mutual TLS

      
Normal TLS proves the server’s identity. Mutual TLS makes the client present a certificate too.

      
With mTLS, both sides hold a private key and a certificate signed by a CA the other side trusts, usually a private internal CA. It’s common for service-to-service traffic inside a company, service meshes (Istio, Linkerd), banking APIs and IoT devices. It’s strong because the credential is a private key that never crosses the network, but issuing, rotating and revoking certificates is real operational work, and it’s awkward for end users in browsers.

      
OAuth can also bind tokens to a client certificate (or to a key via DPoP) so a stolen token is useless without the matching private key.

    


    
Delegation and federation


    

      
OAuth 2.0

      
A way to let one app act on your behalf at another service, without giving it your password.

      
The classic example: a printing app wants your Google Photos. Instead of asking for your Google password, it sends you to Google, you approve “view your photos,” and Google gives the app a token limited to that permission. That’s delegated authorization. OAuth by itself doesn’t tell the app who you are; that’s what OpenID Connect adds.

      
The four roles

      
    
        
  • Resource owner: you, the user who owns the data.
    • 
        
  • Client: the app that wants access (the printing app).
    • 
        
  • Authorization server: authenticates you and issues tokens (Google’s login and consent screens).
    • 
        
  • Resource server: the API holding the data (Google Photos API). It accepts access tokens.
    • 
      

      
Authorization code flow with PKCE

      
This is the recommended flow for nearly every app with a user: web, mobile and single-page. PKCE (“pixie,” Proof Key for Code Exchange) stops someone who intercepts the short-lived code from redeeming it.

      

# Step 1: send the user here
https://auth.example.com/authorize
  ?response_type=code
  &client_id=print-app
  &redirect_uri=https://print.app/callback
  &scope=photos.read
  &state=xyz123                     # CSRF protection, checked on return
  &code_challenge=E9Melhoa2Owv...   # BASE64URL(SHA256(code_verifier))
  &code_challenge_method=S256

# Step 2: back-channel exchange, server to server
POST /token
grant_type=authorization_code&code=SplxlOB...&redirect_uri=...&code_verifier=dBjftJeZ4CVP...

Scopes are the permission strings the client requests (photos.read, calendar.write). The user sees them on the consent screen, and the resource server checks them on each call.

      
Common OAuth mistakes
Loose redirect URI matching (register exact URIs), skipping the state check, putting client secrets in mobile or browser apps (they’re “public clients” and rely on PKCE instead), and using an access token as proof of login. An access token is meant for the API, not for the client to learn who the user is.

    


    

      
OpenID Connect

      
A thin identity layer on top of OAuth 2.0. It’s what “Sign in with Google” or “Sign in with Apple” actually uses.

      
The flow is the same authorization code flow above, with openid added to the scope. The token response then includes an ID token: a signed JWT, meant for the client, stating who authenticated, when and how.


{
  "iss": "https://accounts.google.com",
  "sub": "110169484474386276334",     // stable user ID: key your accounts on this
  "aud": "your-client-id",
  "exp": 1760650000,
  "iat": 1760646400,
  "nonce": "n-0S6_WzA2Mj",            // echoes your request, prevents replay
  "email": "ada@example.com",
  "email_verified": true,
  "name": "Ada Lovelace"
}

      

        
ID token
For the client. Says who the user is.
Verify signature, iss, aud, exp and nonce.

        
Access token
For the API. Says what the bearer may do.
The client should treat it as opaque.

      

      
OIDC also standardizes a discovery document at /.well-known/openid-configuration (listing endpoints and the JWKS URL), a /userinfo endpoint, and standard scopes like profile and email.

    


    

      
Single sign-on

      
Log in once with a central identity provider, then get into many apps without logging in again.

      
SSO is a pattern, not a protocol. A company runs one IdP (Okta, Microsoft Entra ID, Google Workspace), and every app trusts it. When you open an app, it sends you to the IdP; if you already have a session there, you’re bounced straight back with a signed statement of who you are. Each app then creates its own local session. This is also called federation.

Related pieces you’ll meet in enterprise SSO: SCIM automatically creates and removes user accounts in apps when HR adds or removes people in the IdP, and single logout, which tries to end every app’s session at once, is notoriously unreliable, so short app sessions matter.

Authorization models

      
Once you know who someone is, how do you decide what they can do?

      

        
ModelThe rule looks likeGood for

        
          
ACL (access control list)File 9 lists Ada: read, writePer-object sharing, file systems

          
RBAC (role-based)Editors can publish posts; Ada is an editorMost business apps; easy to reason about

          
ABAC (attribute-based)Allow if user.department = doc.department and time is in business hoursFine-grained, context-aware policies

Scopes and roles combine: a token’s scopes cap what the app may do, and the user’s roles cap what the user may do. The effective permission is the overlap.


# Check authorization on every request, on the server, against the specific object
def update_invoice(user, invoice_id, changes):
    invoice = db.get_invoice(invoice_id)
    if invoice.org_id != user.org_id:       # object-level check
        raise Forbidden()                   # 403
    if "invoices:write" not in user.permissions:
        raise Forbidden()
    invoice.apply(changes)

      
The most common authorization bug
Checking that a user is logged in but not that they own the record. If changing /invoices/1001 to /invoices/1002 shows someone else’s invoice, that’s an IDOR (insecure direct object reference). Hiding a button in the UI is not authorization; the server must check.

      
Principles
Deny by default. Grant the least privilege needed. Centralize policy logic rather than scattering if checks. Log authorization failures.

Choosing an approach

      
Most real systems mix several of these. Start from what you’re building.

      

        
You’re buildingTypical choice

        
          
Server-rendered websiteSession cookies (HttpOnly, Secure, SameSite), passwords hashed with Argon2id, optional passkeys and MFA

          
Single-page app with its own backendSession cookie on the same site, or a BFF that holds OAuth tokens server-side

          
Mobile or desktop appOAuth authorization code with PKCE via the system browser; tokens in Keychain or Keystore

          
“Sign in with Google / Apple / GitHub”OpenID Connect

          
Letting third-party apps access users’ dataBe an OAuth 2.0 authorization server with scopes and consent

          
Employee access to many internal and SaaS appsSSO through a corporate IdP, using SAML or OIDC, plus SCIM provisioning

          
Service-to-service callsOAuth client credentials, mTLS, or cloud workload identity

          
Public developer APIAPI keys for the developer’s account; OAuth when acting for end users

          
CLI or smart TV appOAuth device authorization grant

          
Quick internal tool or scriptBasic auth over HTTPS, or put it behind an SSO proxy

        
      

      
Don’t roll your own
Use a mature framework or identity service (your web framework’s auth module, Auth0, Okta, Keycloak, Cognito, Firebase Auth, Clerk and similar) and spend your effort on configuring it well and on authorization logic, which is specific to your app.

    


    

      
Glossary

      

        
Access token
Short-lived credential an API accepts to authorize requests.

        
Assertion
A signed statement from an IdP about a user, especially in SAML.

        
Audience (aud)
The intended recipient of a token. Services should reject tokens not addressed to them.

        
Bearer token
Any token where possession alone grants access.

        
Certificate authority (CA)
An entity that signs certificates binding public keys to names.

        
Claim
A single fact in a token, such as sub or email.

        
Client ID / client secret
An OAuth app’s username and password. Public clients (mobile, SPA) have no secret.

        
CORS
Browser rules for which origins may read cross-site responses. It isn’t an authentication mechanism and doesn’t protect your server from non-browser callers.

        
CSRF
Tricking a browser into sending an authenticated request the user didn’t intend.

        
DPoP
Demonstrating Proof of Possession: binds an OAuth token to a client-held key.

        
HMAC
A hash mixed with a secret key, proving integrity and authenticity to anyone sharing the key.

        
ID token
OIDC JWT telling the client who the user is.

        
IdP / SP / RP
Identity provider; service provider (SAML’s name for the app); relying party (OIDC’s name for the app).

        
Introspection
An endpoint an API calls to ask the auth server whether an opaque token is active.

        
JWKS
JSON Web Key Set: a published list of public keys for verifying tokens.

        
Nonce
A one-time random value that ties a response to a specific request and prevents replay.

        
PKCE
Proof Key for Code Exchange: ties an OAuth code to the app that requested it.

        
Refresh token
Longer-lived credential used only to obtain new access tokens.

        
Salt / pepper
Per-user random value / app-wide secret mixed into password hashes.

        
Scope
A named permission requested by and granted to an OAuth client.

        
SCIM
Standard API for provisioning and deprovisioning users from an IdP.

        
Session fixation
An attacker plants a known session ID before login. Prevented by issuing a new ID at login.

        
State
OAuth parameter that guards the redirect back to your app against CSRF.

        
Subject (sub)
The stable, unique identifier of the principal a token describes.

        
XSS
Injected script running on your page with your page’s privileges.

        
Zero trust
A security stance where every request is authenticated and authorized, regardless of network location.
