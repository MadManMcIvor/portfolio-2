Containers,
explained

A container is an ordinary process that the Linux kernel fences off so it sees its own files, network and process list. Docker made that easy to package and share. Compose runs several containers together on one machine. Kubernetes runs them across many machines.

The stack on the right is the map of this page. Each layer builds on the one below it; pick one to jump there.

KubernetesRuns containers across a cluster of machines ComposeSeveral containers, one machine, one file ContainersRunning, isolated processes ImagesThe packaged app, built from a Dockerfile Linux kernelNamespaces, cgroups, layered filesystems

Docker and Podman are two different tools for working with the middle layers. Both speak the same open image format, so they’re largely interchangeable.

    What a container actually is

    Before containers, “it works on my machine” was a real problem: your app depended on a specific version of Python, some system libraries and a config file in just the right place, and the server never quite matched your laptop.

    A container solves this by bundling the app with everything it needs to run, its libraries, runtime and files, into one package called an image. When you run the image, you get a container: a normal Linux process that the kernel isolates using two features.

    • Namespaces control what the process can see. It gets its own view of the filesystem, its own network interfaces, its own process IDs (it thinks it’s process 1) and its own hostname.
    • Control groups (cgroups) control what the process can use: how much CPU, memory and disk I/O it’s allowed.

    That’s the whole trick. There’s no separate operating system inside a container, which is why containers start in milliseconds and you can run dozens on a laptop.

    On a Mac or Windows PC? Containers need a Linux kernel, so Docker Desktop, Podman Desktop and similar tools quietly run a small Linux virtual machine and put your containers inside it. That’s why file sharing between your Mac and a container can feel slower than on a Linux machine.

    The vocabulary

    Most confusion comes from mixing up a handful of terms. The colored marks match the layers in the map at the top.

    Image
    A read-only package containing an app and everything it needs. Think of it as a template or a recipe’s finished, frozen meal. Images are made of stacked layers, one per build step, and identical layers are shared between images to save space.
    Container
    A running (or stopped) instance of an image. You can start many containers from one image, just as you can create many objects from one class. Each gets its own thin writable layer on top of the image.
    Dockerfile
    A text file of instructions for building an image: start from this base, copy these files, run this command. Podman reads the same file (it also accepts the name Containerfile).
    Tag
    A human-friendly label on an image, like postgres:16 or myapp:1.4.2. The full name is registry/namespace/name:tag; if you leave out the tag you get latest, which is just a name, not a guarantee of anything new.
    Registry
    A server that stores and serves images. Docker Hub is the default public one; others include GitHub Container Registry (ghcr.io), Quay, and the registries built into AWS, Google Cloud and Azure.
    Volume
    Storage that lives outside a container so data survives when the container is deleted. Essential for databases.
    Port mapping
    Connecting a port on your machine to a port inside a container. -p 8080:80 means “traffic to my port 8080 goes to the container’s port 80.” Host first, container second.
    Network
    A virtual network that containers join so they can talk to each other by name.
    OCI
    The Open Container Initiative, the standards body that defines the image format and how runtimes start containers. It’s the reason an image built with Docker runs on Podman and Kubernetes without changes.

    Build, ship, run

    Every container workflow follows the same path, whichever tool you use. This is a genuine sequence: each step needs the one before it.

    1. WriteDescribe your app’s environment in a Dockerfile.
    2. BuildTurn the Dockerfile into an image.
      docker build -t myapp:1.0 .
    3. PushUpload the image to a registry so other machines can get it.
      docker push ghcr.io/me/myapp:1.0
    4. RunAny machine pulls the image and starts a container.
      docker run ghcr.io/me/myapp:1.0

    On your own laptop you often skip pushing: you build and run locally. Pushing matters once a server, a teammate or a CI pipeline needs the image.

    Reading a Dockerfile

    Here’s a typical Dockerfile for a small Node.js web app, one instruction at a time.

    FROM node:22-alpine

    Start from an existing image that already has Node installed. alpine is a tiny Linux base, which keeps the image small.

    WORKDIR /app

    Create /app inside the image and make it the current folder for the steps that follow.

    COPY package*.json ./

    Copy only the dependency list first. This is deliberate, and the next line explains why.

    RUN npm ci --omit=dev

    Install dependencies. Because this layer only depends on package.json, Docker can reuse it from cache when you change your code but not your dependencies, which makes rebuilds fast.

    COPY . .

    Now copy the rest of your source code. A .dockerignore file keeps things like node_modules and .git out.

    EXPOSE 3000

    Documents which port the app listens on. It doesn’t publish anything by itself; you still need -p when you run it.

    USER node

    Run as an unprivileged user instead of root, a cheap and worthwhile security habit.

    CMD ["node", "server.js"]

    The command that runs when a container starts. When this process exits, the container stops.

    Multi-stage builds

    For compiled languages or front-end builds, use one stage with all the build tools and a second, slim stage that only receives the finished output. The final image ships without compilers or source code.

    FROM golang:1.23 AS build
WORKDIR /src
COPY . .
RUN go build -o /out/server .

FROM gcr.io/distroless/static
COPY --from=build /out/server /server
CMD ["/server"]

    Everyday commands

    These cover the vast majority of day-to-day use. Swap docker for podman and nearly all of them work unchanged.

    CommandWhat it does
    docker run -d -p 8080:80 --name web nginxStart a container in the background (-d), map port 8080 to 80, and give it a name.
    docker run -it --rm alpine shStart an interactive shell in a throwaway container that deletes itself on exit.
    docker ps / docker ps -aList running containers / all containers, including stopped ones.
    docker logs -f webShow and follow a container’s output.
    docker exec -it web shOpen a shell inside an already running container, great for poking around.
    docker stop web / docker start webStop or restart a container without deleting it.
    docker rm webDelete a stopped container (add -f to force-stop it first).
    docker build -t myapp:1.0 .Build an image from the Dockerfile in the current folder.
    docker imagesList images stored locally.
    docker pull / docker pushDownload an image from, or upload one to, a registry.
    docker inspect webShow every detail about a container or image as JSON.
    docker system dfSee how much disk images, containers and volumes are using.
    docker system pruneRemove stopped containers, unused networks and dangling images. Add -a to remove all unused images too.

    Storage and networking

    Containers are disposable, your data isn’t

    Anything a container writes to its own filesystem disappears when the container is removed. That’s a feature: you can throw a container away and start a fresh one from the image at any time. To keep data, put it somewhere outside the container.

    TypeExampleUse it for
    Named volume-v pgdata:/var/lib/postgresql/dataDatabase files and anything the app owns. Docker manages where it lives.
    Bind mount-v ./src:/app/srcDevelopment: your editor changes files on your machine and the container sees them instantly.
    tmpfs--tmpfs /tmpScratch space kept only in memory.

    How containers find each other

    When containers join the same user-defined network, they can reach each other by container name, thanks to built-in DNS. Your web app connects to db:5432, not to an IP address.

    docker network create appnet
docker run -d --name db  --network appnet -e POSTGRES_PASSWORD=secret postgres:16
docker run -d --name web --network appnet -p 8080:3000 myapp:1.0
# inside "web", the database is reachable at db:5432

    Port mapping (-p) is only needed for traffic coming from outside, such as your browser. Containers on the same network talk to each other directly on their internal ports. Typing all of this by hand gets old fast, which is exactly what Compose fixes.

    Docker Compose

    Real apps are rarely one container. A web app usually needs a database, maybe a cache and a background worker. Compose lets you describe all of them, plus their networks and volumes, in a single compose.yaml file, then start or stop the whole set with one command.

    compose.yaml 
    services:
  web:
    build: .                          # build from the Dockerfile here
    ports:
      - "8080:3000"
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
    depends_on:
      db:
        condition: service_healthy     # wait until the db is actually ready
    develop:
      watch:                          # auto-sync code with "docker compose watch"
        - action: sync
          path: ./src
          target: /app/src

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 5

volumes:
  db-data:

    Compose automatically creates a private network for the project, so web reaches the database simply as db. Each service name becomes a hostname.

    CommandWhat it does
    docker compose up -dBuild if needed and start everything in the background.
    docker compose up -d --buildForce a rebuild of images first, after you’ve changed the Dockerfile or code.
    docker compose psStatus of this project’s containers.
    docker compose logs -f webFollow one service’s logs (leave off the name for all of them).
    docker compose exec db psql -U appRun a command inside a running service.
    docker compose watchSync or rebuild automatically as you edit files.
    docker compose downStop and remove the containers and network. Volumes are kept.
    docker compose down -vSame, but also delete volumes. This wipes the database.

    Two small things that trip people up. The modern command is docker compose (a space, built into Docker). The older standalone docker-compose with a hyphen is retired. And the version: line you’ll see at the top of old examples is no longer needed; you can delete it.

    Compose is ideal for local development, test environments and small single-server deployments. Its limit is right there in the description: it manages containers on one machine. If that machine dies, everything does.

    How the pieces fit together

    “Docker” is really several programs stacked on top of each other, and other tools swap out different layers. Reading each column top to bottom shows what happens when you start a container.

    Docker
    Podman
    Kubernetes
    What you type
    docker CLI
    podman CLI
    kubectl sends YAML to the API server
    Manager
    dockerdA background daemon, traditionally running as root
    No daemonEach container is a child of your own user session
    kubeletAn agent on every node, told what to run by the control plane
    Container runtime
    containerd
    conmonA tiny monitor per container
    containerd or CRI-OPlugged in via the Container Runtime Interface
    Low-level runtime
    runc
    crun or runc
    runc or crun
    Shared standard
    OCI image and runtime specifications, the common format every column reads and writes
    Foundation

    A few things become clear from this picture.

    • Images are portable across all three. Because everyone follows the OCI format, you can build with Docker, test with Podman and deploy to Kubernetes using the very same image.
    • Kubernetes doesn’t need Docker. It talks directly to containerd or CRI-O. When you heard “Kubernetes dropped Docker” around 2022, it meant only this: Kubernetes stopped using the Docker daemon as a middleman. Images built with Docker still run fine.
    • The real work is done at the bottom. runc and crun are small programs that ask the kernel to set up namespaces and cgroups, then start your process. Everything above them is management and convenience.

    Podman and other alternatives

    Podman, backed by Red Hat, is the best-known alternative to Docker. It was designed as a drop-in replacement, so many people simply run alias docker=podman. The differences that matter:

    • No daemon. There’s no always-running background service. Containers are ordinary child processes, which is simpler and removes a single point of failure.
    • Rootless by default. Containers run under your normal user account. If something escapes a container, it lands as you, not as root. Docker can run rootless too, but it’s an extra setup step.
    • Pods. Podman can group containers into a pod that shares a network, the same idea Kubernetes uses. It can even export them as Kubernetes YAML with podman generate kube and run Kubernetes YAML locally with podman kube play.
    • systemd integration. On Linux servers, Podman’s Quadlet files let you run containers as regular system services that start on boot and restart on failure.
    • Compose. podman compose works with the same compose.yaml files, by handing off to a Compose provider installed on your system.

    Image names are one small difference: Podman prefers fully qualified names like docker.io/library/nginx rather than assuming Docker Hub.

    Kubernetes

    Compose runs containers on one machine. Kubernetes (often written K8s) runs them across a cluster of machines and keeps them running. Instead of telling it “start this container,” you describe the state you want, such as “three copies of my web app, reachable on port 80,” and Kubernetes works continuously to make reality match. If a machine fails, it reschedules the containers elsewhere. If traffic grows, it can add copies.

    That power comes with real complexity: many new concepts, more YAML, and a cluster that itself needs care. That’s why many teams use a managed service such as Amazon EKS, Google GKE or Azure AKS, where the cloud provider runs the control plane for you.

    The core objects

    Cluster
    The whole system: a control plane that makes decisions, plus nodes that run your workloads.
    Node
    One machine (physical or virtual) in the cluster. Each node runs the kubelet and a container runtime.
    Pod
    The smallest unit Kubernetes runs: one or more containers that share an IP address and storage. Usually one main container per pod. Pods are disposable and get replaced, not repaired.
    Deployment
    Says “keep N identical pods running from this image.” It handles rolling updates and rollbacks when you change the image version.
    Service
    A stable name and IP in front of a changing set of pods, with load balancing. Pods come and go; the Service stays put. This is Kubernetes’ version of Compose’s service-name DNS.
    Ingress / Gateway
    Routes outside HTTP traffic to Services, for example by domain name or URL path.
    ConfigMap / Secret
    Configuration and sensitive values kept separate from images and injected into pods.
    PersistentVolumeClaim
    A request for storage that outlives any pod. The equivalent of a named volume.
    Namespace
    A way to divide one cluster into separate areas, such as per team or per environment.

    A minimal example

    This runs three copies of a web app and gives them one stable address inside the cluster.

    web.yaml 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: ghcr.io/me/myapp:1.0
          ports:
            - containerPort: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector: { app: web }
  ports:
    - port: 80
      targetPort: 3000
    kubectl apply -f web.yaml          # create or update everything in the file
kubectl get pods                   # see the three pods
kubectl logs deploy/web            # logs from the deployment's pods
kubectl port-forward svc/web 8080:80   # reach it from your laptop
kubectl delete -f web.yaml         # remove it all

    Trying it locally

    You don’t need cloud servers to learn. kind runs a cluster inside Docker containers, minikube runs one in a VM or container, k3d runs the lightweight k3s distribution in Docker, and Docker Desktop and Rancher Desktop each have a single-node cluster you can switch on. Helm is the common package manager for installing ready-made apps onto a cluster.

    Other orchestrators exist. Docker Swarm is built into Docker and uses Compose-style files; it’s simpler than Kubernetes but much less widely adopted. HashiCorp Nomad is another option. Many apps also skip orchestration entirely by using a managed container platform such as Google Cloud Run, AWS Fargate or Azure Container Apps, where you hand over an image and the provider runs it.

    One app, four ways

    The same task, running the nginx web server so it’s reachable on port 8080, expressed in each tool. Notice how the image name stays the same throughout.

    One command. Good for trying things out and single containers.

    docker run -d --name web -p 8080:80 nginx:1.27
# open http://localhost:8080

    Identical apart from the command name and the fully qualified image. Runs as your user, with no daemon.

    podman run -d --name web -p 8080:80 docker.io/library/nginx:1.27
# open http://localhost:8080

    The same settings written down in a file, so they’re repeatable and easy to extend with more services.

    # compose.yaml
services:
  web:
    image: nginx:1.27
    ports:
      - "8080:80"

# then run:
docker compose up -d

    You declare the desired state and Kubernetes keeps it that way, here with two copies behind a Service.

    # nginx.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 2
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
        - { name: web, image: nginx:1.27, ports: [{ containerPort: 80 }] }
---
apiVersion: v1
kind: Service
metadata: { name: web }
spec:
  selector: { app: web }
  ports: [{ port: 80 }]

# then run:
kubectl apply -f nginx.yaml
kubectl port-forward svc/web 8080:80

    What to use when

    Most people don’t need everything on this page. Start at the simplest level that solves the problem and move up only when you feel the pain.

    I want to try a tool or database without installing it.

    A single docker run or podman run.

    My app has a few parts (web, database, cache) and I develop it locally.

    Docker Compose.

    I want daemonless, rootless containers, or I’m on Fedora or RHEL.

    Podman, which works with your existing Dockerfiles and Compose files.

    I’m hosting a small app on one server.

    Compose on that server, or Podman with Quadlet as a system service.

    I just want my container running in the cloud without managing servers.

    A managed platform such as Cloud Run, Fargate or Azure Container Apps.

    Many services, several machines, zero-downtime deploys, autoscaling, a team to look after it.

    Kubernetes, ideally a managed one (EKS, GKE, AKS).

    Common gotchas

    “My container exits immediately”
    A container lives exactly as long as its main process. If your CMD finishes or crashes, the container stops. Check docker logs to see why.
    “I can’t reach my app”
    Inside a container, localhost means the container itself. Make your app listen on 0.0.0.0, not 127.0.0.1, and make sure you published the port with -p.
    “My data vanished”
    Data written inside a container is deleted with it. Use a volume for anything you care about, and be careful with docker compose down -v.
    “The image works on my Mac but not on the server”
    Apple Silicon Macs build arm64 images by default, while most servers are amd64. Build for the target with --platform linux/amd64, or build for both with docker buildx.
    “Every build is slow”
    Put steps that rarely change (installing dependencies) before steps that change often (copying source code), and add a .dockerignore.
    “Which version is latest?”
    Whatever was last pushed under that name. Pin specific tags like postgres:16 so builds are predictable.
    “My disk is full”
    Old images and build cache pile up. Check with docker system df and clean up with docker system prune.
    “I put a password in the Dockerfile”
    Anyone with the image can read it, even if a later step deletes the file, because earlier layers are kept. Pass secrets at run time through environment variables, Compose secrets or Kubernetes Secrets.
