A working reference for Go

A one-page Go reference for developers who already know at least one other language. Each topic explains how Go handles it and, where Go takes a different path, compares it with Python, JavaScript, TypeScript and Java.

This guide reflects Go 1.27, released 19 August 2026. The current patch is 1.27.2 (8 October 2026). Go supports the two newest major releases, so 1.27 and 1.26 get security fixes and 1.25 no longer does.

Features added after Go 1.21 carry a tag like Go 1.24+, so you can tell what works on an older toolchain. Check yours with go version.

Each topic follows the same order: the idea in plain words, a step-through visual where one helps, code with a copy button, comparisons with other languages, when to reach for it, what to watch out for, and a notes box. Notes are saved in this browser as you type.

Philosophy, trade-offs and where Go is used

Go is a small, deliberately plain language for building network services and tools that large teams can read and maintain. Robert Griesemer, Rob Pike and Ken Thompson started it at Google in 2007, frustrated by slow C++ builds and complex code. Go 1.0 shipped in 2012 with a compatibility promise that still holds: code written for Go 1.0 generally builds today.

The design goal is that a stranger can open any Go file and follow it. That means one formatting style, one loop keyword, few ways to do each thing, and no hidden control flow: no exceptions jumping up the stack, no operator overloading, no implicit conversions, no inheritance. Two releases a year (February and August) add features slowly.

Where it's used

Go dominates cloud infrastructure: Kubernetes, Docker and containerd, Terraform, Prometheus, etcd and most CNCF projects are written in it. It's common for CLIs (GitHub's gh, Hugo, k9s), proxies and networking (Caddy, Traefik), databases (CockroachDB, Vitess, InfluxDB) and backend services at Google, Uber, Cloudflare, Twitch, Dropbox and many others. Microsoft's native port of the TypeScript compiler is also written in Go, chosen partly because Go's plain structure let the existing codebase be ported file by file.

The same tiny service in each language

A JSON-free "hello" endpoint shows the batteries-included standard library. The Go version needs no dependencies, serves each request on its own goroutine, and deploys as one file.

main.go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	mux := http.NewServeMux()
	// Method + path wildcard patterns: Go 1.22+
	mux.HandleFunc("GET /hello/{name}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "hello, %s\n", r.PathValue("name"))
	})
	log.Fatal(http.ListenAndServe(":8080", mux))
}

What's different: Python and Node need a framework (or hand-rolled routing) to get here; Java's built-in server works but most teams reach for Spring. Go's net/http is what production Go services actually run on, so the stdlib is the default rather than a toy.

Reach for it when

  • You're building network services, APIs, proxies or anything that spends its life waiting on I/O.
  • You want CLIs and dev tools that ship as one binary with no runtime to install.
  • Several teams will maintain the code for years and readability beats cleverness.
  • You need real parallelism without the ceremony of thread pools or async runtimes.

Watch out for

  • Data science and ML: Python's ecosystem has no Go equivalent.
  • UI work, browser front ends and mobile apps.
  • Hard real-time or no-GC systems, where Rust, C or C++ fit better.
  • Domains that want rich type modeling: Go has no sum types or pattern matching.
  • Quick throwaway scripts, where Python is faster to write.

Toolchain: install, run, build, test, debug

Everything ships in one go command: build, run, test, format, vet, docs, dependency management and toolchain updates. There is no separate package manager, test runner or formatter to choose. That single tool is the biggest day-one difference from npm, pip or Maven.

Install and keep up to date

Download an installer from go.dev/dl, or use brew install go (macOS), winget install GoLang.Go (Windows) or the Linux tarball into /usr/local/go. After that, Go manages its own versions: the go line in go.mod sets the minimum language version, and with the default GOTOOLCHAIN=auto the go command downloads a newer toolchain automatically when a module needs one. That replaces pyenv, nvm or SDKMAN for most people.

Everyday commands
# Start a module. The path is an identifier; it needn't exist online yet.
mkdir hello && cd hello
go mod init example.com/hello

go run .                      # compile and run the package in this directory
go build -o bin/hello .       # write a native binary
GOOS=linux GOARCH=arm64 go build -o bin/hello-linux .   # cross-compile, no setup
go install example.com/cmd/tool@latest                   # install a CLI into $GOBIN

go test ./...                 # every package below here
go vet ./...                  # built-in correctness checks
go fix ./...                  # apply modernizers (rewritten in Go 1.26)
go fmt ./...                  # gofmt every file
go doc net/http.Client        # docs in the terminal
go env GOPATH GOMODCACHE      # where things live

Project layout

There's no src/ directory and no required structure. A package is a directory; a module is the tree under a go.mod. Start flat and split when a file gets unwieldy. The widely copied "golang-standards/project-layout" repo is not official, and a pkg/ directory is optional at best.

Since Go 1.26+, go mod init writes the previous release as the go version (so Go 1.27 writes go 1.26.0), which keeps new modules usable on every supported toolchain. Raise it with go get go@1.27 when you need a newer feature.

Dependencies

go get example.com/lib@v1.4.0 adds or changes a requirement; go mod tidy adds what imports need and removes what they don't. Downloads go through proxy.golang.org and are verified against the public checksum database, so a tampered tag is caught. For private repositories set GOPRIVATE=github.com/yourco/*.

Go resolves versions with minimal version selection: if two packages need v1.2 and v1.5 of a library, you get v1.5, the lowest version satisfying everyone, and never a surprise newer one. There are no version ranges like ^1.2.0, so go.mod already pins exact versions and go.sum only stores checksums. Use replace for a local fork and go work for editing several modules together.

Formatting and linting

gofmt has no configuration and everyone runs it, usually on save via gopls, the official language server behind VS Code's Go extension and other editors. goimports also fixes the import block. go vet ships with the toolchain and catches real bugs (bad Printf verbs, copied mutexes, unreachable code). Most teams add staticcheck or run golangci-lint (version 2, configured in .golangci.yml) which bundles many linters. govulncheck reports only vulnerabilities your code actually calls. Since Go 1.26+, go fix rewrites code to modern idioms, for example replacing hand-written loops with slices.Contains or min.

Testing

Tests are functions named TestXxx(t *testing.T) in _test.go files next to the code. No framework is needed; the idiom is a table of cases run as subtests.

parse_test.go
package parse

import "testing"

func TestAtoiStrict(t *testing.T) {
	tests := []struct {
		name    string
		in      string
		want    int
		wantErr bool
	}{
		{"simple", "42", 42, false},
		{"negative", "-7", -7, false},
		{"empty", "", 0, true},
		{"spaces", " 1", 0, true},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := AtoiStrict(tt.in)
			if (err != nil) != tt.wantErr {
				t.Fatalf("AtoiStrict(%q) error = %v, wantErr %v", tt.in, err, tt.wantErr)
			}
			if got != tt.want {
				t.Errorf("AtoiStrict(%q) = %d, want %d", tt.in, got, tt.want)
			}
		})
	}
}

func BenchmarkAtoiStrict(b *testing.B) {
	for b.Loop() { // Go 1.24+: replaces the old `for i := 0; i < b.N; i++`
		AtoiStrict("123456")
	}
}

func FuzzAtoiStrict(f *testing.F) {
	f.Add("42")
	f.Fuzz(func(t *testing.T, s string) {
		AtoiStrict(s) // the fuzzer looks for panics and failed checks
	})
}

Debugging and profiling

Delve is the debugger: go install github.com/go-delve/delve/cmd/dlv@latest, then dlv debug ./cmd/hello or dlv test ./internal/store -- -test.run TestGet. VS Code and GoLand drive Delve for you. For quick inspection, fmt.Printf("%+v\n", x) prints struct fields by name and %#v prints Go syntax.

Profiling is built in. Add import _ "net/http/pprof" to a service, or run go test -cpuprofile cpu.out, then go tool pprof -http=:0 cpu.out opens a web UI that defaults to a flame graph Go 1.26+. go tool trace shows scheduler behavior, and the goroutineleak profile reports goroutines that can never wake up Go 1.27+.

  • Assuming the test cache is stale; it's keyed on inputs and is usually right.

Syntax essentials and the type system

Go reads like C with the clutter removed: no parentheses around conditions, mandatory braces, no semicolons (the compiler inserts them at line ends, which is why { must sit on the same line). Types come after names. Every type has a zero value, so a declared variable is always usable. There are no implicit conversions and no truthiness: an if needs a real bool.

basics.go
package main

import (
	"fmt"
	"strings"
)

const Pi = 3.14159 // untyped constant: takes whatever numeric type the context needs

type Weekday int // a new named type, not interchangeable with int

const (
	Sunday Weekday = iota // 0
	Monday                // 1: the expression repeats with iota incremented
	Tuesday               // 2
)

func main() {
	var count int           // zero value: 0
	name := "gopher"        // := declares and infers (inside functions only)
	x, y := 3, 2.5          // int and float64
	total := float64(x) + y // conversions are always explicit

	if n := len(name); n > 3 { // init statement, scoped to the if/else
		fmt.Println("long name:", n)
	}

	for i := 0; i < 3; i++ { // the classic three-part loop
		count += i
	}
	for count < 10 { // "while"
		count++
	}
	for i := range 3 { // range over an int, Go 1.22+
		fmt.Print(i, " ")
	}
	for i, r := range "héllo" { // ranging a string yields runes and byte offsets
		fmt.Println(i, string(r))
	}

	switch day := Monday; day { // cases don't fall through
	case Sunday:
		fmt.Println("weekend")
	case Monday, Tuesday:
		fmt.Println("early week")
	default:
		fmt.Println("later")
	}

	switch { // tagless switch: a tidy if/else-if chain
	case total > 5:
		fmt.Println("big")
	default:
		fmt.Println("small")
	}

	fmt.Println(strings.ToUpper(name), count, total, Pi)
}

A few rules carry most of the weight. Static typing is checked at compile time with local inference. type Celsius float64 creates a distinct named type: you can attach methods to it, and mixing it with plain float64 needs a conversion. type Temp = float64 is an alias, just another name. Untyped constants are exact until used, so const big = 1 << 100 is fine as long as you only use it in contexts that fit. Strings are byte sequences: len counts bytes and indexing yields bytes, while range decodes runes. nil exists only for the reference-like kinds, so an int or string can never be "missing".

Recent additions: min, max and clear built-ins Go 1.21+, range over integers Go 1.22+, range over iterator functions Go 1.23+, and new(expr) Go 1.26+, which allocates a variable initialized to a value, handy for optional pointer fields: Age: new(42).

Why Go differs: implicit conversions and truthiness are where silent bugs live, so Go removes both and accepts a little more typing. Named types give you cheap, checked domain types (IDs, units, enums) without classes. Zero values remove a whole category of "uninitialized" errors: a struct, map lookup or variable always has a defined value.

Reach for it when

  • := for most locals; var x T when the zero value is what you want.
  • Named types for units, IDs and enums, so the compiler stops you mixing them.
  • Tagless switch instead of long if/else if chains.
  • for i := range n and range over strings, slices, maps and iterators.
  • Constants with iota plus a String() method (or stringer) for enums.

Watch out for

  • := in an inner scope shadowing an outer variable, especially err.
  • Unused variables and imports are compile errors, not warnings. Use _ while sketching.
  • Integer overflow wraps silently; integer division truncates (7/2 == 3).
  • len("é") is 2: lengths are bytes. Use utf8.RuneCountInString for characters.
  • iota enums aren't exhaustive: nothing stops Weekday(42). Validate at boundaries.

Collections and data structures

Three built-ins carry nearly all data in Go: slices (growable views onto arrays), maps (hash tables) and structs (records). Arrays exist, but their length is part of their type and they copy like any value, so you rarely use them directly. There's no built-in set, list, deque or tree; you compose them or reach for the slices, maps and container/... packages.

A tour (fragment)
nums := []int{3, 1, 2}              // slice literal

buf := make([]byte, 0, 4096)        // length 0, capacity 4096: preallocated

Transforming collections

Go has no map/filter on slices and no comprehensions. A loop is the idiom, and it's usually shorter than it looks once you stop fighting it.

// Preallocate when you know the upper bound.
adults := make([]string, 0, len(users))
for _, u := range users {
	if u.Age >= 18 {
		adults = append(adults, u.Name)
	}
}

adults = [u.name for u in users if u.age >= 18]

Why: Go values code whose cost is visible. A loop shows exactly one pass and one allocation strategy; a chain of lambdas hides intermediate slices. Generic helpers do exist for search, sort, equality, min/max, insert and delete in slices, and maps.Keys, maps.Values, slices.Collect work with iterators.

Iterators Go 1.23+

An iterator is a function that takes a yield callback. for range drives it, and returning false from yield means the loop body hit break. It's push-style, unlike Python generators or Java's Iterator, but it reads the same at the call site.

evens.go
import "iter"

// Evens yields 0, 2, 4, … below limit.
func Evens(limit int) iter.Seq[int] {
	return func(yield func(int) bool) {
		for n := 0; n < limit; n += 2 {
			if !yield(n) { // the consumer stopped early
				return
			}
		}
	}
}

func main() {
	for n := range Evens(100) {
		if n > 6 {
			break
		}
		fmt.Println(n) // 0 2 4 6
	}
	firstTen := slices.Collect(Evens(20)) // drain into a slice
	fmt.Println(firstTen)
}

The Python and JavaScript equivalent is a generator (def with yield, or function*). iter.Seq2[K, V] yields pairs, which is how maps.All and slices.All work.

Reach for it when

  • A slice for any ordered collection; make([]T, 0, n) when you know the size.
  • map[K]struct{} as a set, and struct keys instead of building "a:b" strings.
  • slices and maps helpers before writing your own search or sort.
  • slices.Sorted(maps.Keys(m)) when output must be deterministic.
  • An iterator (iter.Seq) when a sequence is large, lazy or expensive to build.

Watch out for

  • append aliasing: two appends to one slice can overwrite each other (step through above).
  • Writing to a nil map panics: var m map[string]int; m["a"] = 1. Appending to a nil slice is fine.
  • Map iteration order changes between runs; tests that depend on it flake.
  • m[k].Field = v doesn't compile for struct values; store pointers or reassign the whole struct.
  • A small subslice of a huge array keeps the whole array alive. slices.Clone it if you keep it.

Functions, closures and generics

Functions are first-class values. They can return several results, which is how Go returns errors without exceptions and pairs without tuples. Closures capture variables, not snapshots. Methods are functions with a receiver. Generics Go 1.18+ let functions and types take type parameters, constrained by interfaces, and since Go 1.27+ methods can declare their own type parameters too.

funcs.go
// Several results; the error goes last by convention.
func divmod(a, b int) (q, r int, err error) {
	if b == 0 {
		return 0, 0, errors.New("divide by zero")
	}
	return a / b, a % b, nil
}

An error in Go is any value with an Error() string method. Functions return it as their last result and the caller checks it straight away. Wrapping with fmt.Errorf("context: %w", err) adds context while keeping the original inspectable. There are no exceptions; panic is reserved for bugs.

Objects and code reuse: structs, methods, interfaces, embedding

Go has types with methods but no classes and no inheritance. You build behavior from four pieces: structs hold data, methods attach behavior to any named type, interfaces describe behavior and are satisfied implicitly, and embedding composes types by promoting the inner type's fields and methods.

Receivers and method sets

Use a pointer receiver when the method mutates, when the struct contains a sync.Mutex, or when it's large; otherwise a value receiver is fine. Keep one style per type. The rule that bites: the method set of T contains only value-receiver methods, while *T has both. If Inc has a pointer receiver, a Counter value doesn't satisfy interface{ Inc() }, but *Counter does.

Embedding is not inheritance

Promoted methods run with the inner value as their receiver. There's no virtual dispatch back to the outer type, so the "template method" pattern from Java doesn't work.

Go
type Base struct{}

func (Base) Name() string    { return "base" }
func (b Base) Hello() string { return "hello from " + b.Name() }

type Derived struct{ Base }

func (Derived) Name() string { return "derived" }

func main() {
	fmt.Println(Derived{}.Hello()) // "hello from base": Hello's receiver is the Base
}

To get overridable behavior, pass the varying part in as an interface or function field. Since Go 1.27+, struct literals can set fields promoted through embedding directly instead of spelling out the inner struct.

Concurrency: goroutines, channels and sync

A goroutine is a function running concurrently with the rest of the program. Start one with go f(). The runtime multiplexes many goroutines onto a few OS threads and parks a goroutine whenever it blocks on I/O, a lock or a channel, so blocking code is fine: there's no async/await and no split between sync and async functions. Goroutines start with a few kilobytes of stack, so a server can run hundreds of thousands.

Goroutines coordinate through channels (typed pipes that hand values from one goroutine to another) or through shared memory guarded by sync primitives. Use whichever is clearer. Channels suit hand-offs and pipelines; a mutex suits a shared map or counter.

Fan-out with a limit, first error cancels the rest
import "golang.org/x/sync/errgroup"

func fetchAll(ctx context.Context, urls []string) ([]int, error) {
	sizes := make([]int, len(urls))
	g, ctx := errgroup.WithContext(ctx)
	g.SetLimit(4) // at most 4 requests in flight
	for i, u := range urls {
		g.Go(func() error { // i and u are fresh per iteration (Go 1.22+)
			n, err := fetchSize(ctx, u)
			if err != nil {
				return fmt.Errorf("fetch %s: %w", u, err)
			}
			sizes[i] = n // each goroutine writes its own index: no race
			return nil
		})
	}
	err := g.Wait() // waits for all; ctx was cancelled at the first error
	return sizes, err
}

Cancellation with context

context.Context carries deadlines, cancellation and request-scoped values down a call tree. Memory model: GC, values and pointers

Go is garbage collected, so you never free memory. What's different from Python, JavaScript and Java is that Go has value semantics: assignment and argument passing copy the value, and structs and arrays are values, not references to objects. Pointers make sharing explicit. Whether a value lives on the stack or the heap is decided by the compiler's escape analysis, not by you.

The garbage collector

Go's collector is concurrent, non-moving and non-generational. It trades some CPU for short pauses, typically well under a millisecond. Since Go 1.26+ the default is the "Green Tea" collector, which the Go team measured cutting GC overhead by roughly 10 to 40 percent in GC-heavy programs. You get two knobs: GOGC (default 100: collect when the heap grows 100% over the live set) and GOMEMLIMIT, a soft memory cap you should set in containers. Compare that with the JVM's many collectors and flags.

To find allocations, run go build -gcflags=-m to see escape decisions, go test -bench . -benchmem for allocations per operation, and pprof's heap profile. Common fixes: preallocate slices, reuse buffers, use strings.Builder, avoid converting values to interfaces in hot loops, and pool short-lived objects with sync.Pool. For cleanup tied to garbage collection, runtime.AddCleanup replaces SetFinalizer Go 1.24+; the weak package offers weak pointers Go 1.24+; unique interns values Go 1.23+.

Modules, packages and visibility

A package is a directory of .go files that all declare the same package name. A module is a tree of packages versioned together, defined by its go.mod. Visibility has one rule: a name starting with an uppercase letter is exported from its package; anything else is private to the package. Files in the same package see each other's private names. internal/ directories limit who may import a package.

Rules that shape Go code

  • Package names are short, lowercase, single words, and usually match the last element of the import path. Avoid util, common, helpers and models; name packages for what they provide.
  • Callers always write the package name, so names read as phrases: store.New, http.Client, bytes.Buffer. Don't repeat it: http.HTTPClient stutters.
  • Import cycles are compile errors. That forces a layering you'd otherwise only get by discipline.
  • Code under a/b/internal/ is importable only from within a/b/. It's the Go version of keeping an API private across a whole subtree.
  • Major versions 2 and up change the import path: example.com/lib/v2. A v1 and a v2 can coexist in one build.
  • func init() runs automatically at startup, once per file. Keep it for registering things, never for I/O or anything that can fail.
  • import _ "image/png" imports for side effects only (registration). Avoid dot imports.
  • Tests can live in the same package (white-box) or in package store_test (black-box, sees only exported names).
Go
package store

type Store struct {
	data map[string]string // lowercase: private to the package (all its files)
}

func New() *Store { return &Store{data: map[string]string{}} } // capital: exported

Why: the package, not the class or file, is Go's unit of encapsulation. Two levels (exported or not) are enough because there's no inheritance and so nothing to "protect". Capitalization makes visibility obvious at every use site without a keyword.

Reach for it when

  • A package per cohesive idea, named for what it provides.
  • internal/ for everything you don't intend as a public API.
  • A package doc comment (// Package store …) above the package clause.
  • package foo_test for tests that should use only the public API.
  • go work when you're editing two modules at once.

Watch out for

  • Deep trees mirroring Java packages: com/company/service/impl/....
  • Splitting one concept across packages and then fighting import cycles.
  • init() that reads files, environment or the network.
  • Exporting everything "just in case": it becomes API you must keep.
  • Mutable package-level variables; pass dependencies explicitly.

Idiomatic style: what good Go looks like

Good Go is boring Go: gofmt'd, short functions, the happy path running down the left edge with errors handled and returned early, small interfaces defined by whoever consumes them, concrete types returned, and packages named for what they provide. The shared references are Effective Go, the Go Code Review Comments wiki and Google's Go style guide.

Principles worth internalizing

  • Make the zero value useful: var mu sync.Mutex and var b bytes.Buffer work without constructors. Design your types the same way when you can.
  • Accept interfaces, return structs. Define interfaces where they're consumed, with only the methods used.
  • Write synchronous APIs and let callers add goroutines. A function that secretly starts goroutines is hard to test and stop.
  • ctx context.Context is the first parameter of anything that blocks; never a struct field.
  • Libraries don't panic, don't log on the caller's behalf, and don't call os.Exit.
  • Prefer an options struct over long parameter lists and boolean flags like Fetch(url, true, false).
  • "A little copying is better than a little dependency." Ten lines duplicated beats a new module.
  • Run go vet, staticcheck and go fix routinely; they encode much of this guide.

Reach for it when

  • Early returns that keep the success path unindented.
  • Table-driven tests with t.Run subtests.
  • Concrete types until a second implementation or a test needs an interface.
  • Plain for loops over clever generic helpers when either works.
  • Comments that explain why; the code already says what.

Watch out for

  • Interface pollution: an interface per struct, defined beside the struct.
  • utils, helpers, common, models packages that collect unrelated code.
  • Getters and setters for every field; exported fields are fine for plain data.
  • Fire-and-forget goroutines with no way to stop them or collect their errors.
  • any parameters, init() side effects, global mutable state, naked returns in long functions.

nil != nil

Gotchas

Mistakes that catch developers new to Go, and occasionally experienced ones. Where the surprise comes from how other languages behave, a note underneath says how.

A nil pointer in an interface isn't nil

return p where p is a nil *MyErr produces a non-nil error. Declare results as error and return literal nil on success. The step-through is in the objects topic.

In Java and TypeScript, null carries no type information, so this trap doesn't exist there.

Two appends to one slice can share memory

t := append(s, 1); u := append(s, 2) may leave t and u pointing at the same slot. Always use the slice append returns, and slices.Clone when you need independence. The step-through is in the collections topic.

Python lists, JavaScript arrays and Java ArrayLists never alias this way.

range gives you copies

Go
for _, u := range users {
	u.Active = true // changes a copy; users is untouched
}
for i := range users {
	users[i].Active = true // changes the element
}

In Python, JavaScript and Java, the loop variable refers to the element object itself.

Strings are bytes

Go
s := "héllo"
fmt.Println(len(s))                    // 6 bytes, not 5 characters
fmt.Println(s[1])                      // 195: a byte, not "é"
fmt.Println(utf8.RuneCountInString(s)) // 5
fmt.Println(string([]rune(s)[1]))      // é

Python counts code points, JS and Java count UTF-16 units. Go counts bytes.

time.Sleep(100) sleeps 100 nanoseconds

time.Duration is an int64 count of nanoseconds, and an untyped constant converts silently. Write 100 * time.Millisecond. The same applies to timeouts and tickers.

JavaScript's setTimeout(fn, 100) and Java's Thread.sleep(100) take milliseconds; Go takes a typed duration.

:= quietly shadows

Go
var cfg *Config
if path != "" {
	cfg, err := load(path) // declares a NEW cfg inside the if
	if err != nil {
		return err
	}
	_ = cfg
}
use(cfg) // still nil
// Fix: declare err first, then assign with =
// var err error; cfg, err = load(path)

Most languages mark declarations with a keyword (let, var, a type name). := both declares and assigns, which makes shadowing easy to miss.

The loop-variable fix depends on your go.mod

Since Go 1.22, each loop iteration gets fresh variables, so closures and goroutines capture the value you expect. That behavior applies per module based on the go line in go.mod. A module that still says go 1.21 keeps the old shared-variable semantics even when built with Go 1.27.

Matches JavaScript's let; Python's late-binding lambdas still have the old problem.

Nil maps panic on write; nil slices don't

var m map[string]int reads fine (m["x"] is 0) but m["x"] = 1 panics. Initialize with make or a literal. A nil slice works with append, len and range.

A nil Go map acts like an empty, read-only map. In Java a null map throws on any access.

break inside switch breaks the switch

Go
loop:
	for {
		switch ev := next(); ev.Kind {
		case "quit":
			break loop // a plain break would only leave the switch
		case "skip":
			continue
		}
	}

Java and JavaScript need break to stop fallthrough. Go's cases don't fall through, so break inside a switch is rarely needed for that.

Goroutine panics take down the process

An unrecovered panic in any goroutine crashes the whole program, and recover only works in a deferred function in the same goroutine. net/http recovers panics in handlers, but your own background goroutines are on their own.

In Java an uncaught exception ends only its own thread; in Node an unhandled rejection can be caught by a process-level handler.

JSON only sees exported fields

Go
type User struct {
	Name     string    `json:"name"`
	password string    // lowercase: silently skipped by encoding/json
	Created  time.Time `json:"created,omitzero"` // omitzero: Go 1.24+
	Tags     []string  `json:"tags,omitempty"`
}

omitempty never omits a zero struct like time.Time; omitzero does. Decoding into any turns every number into float64. Since Go 1.27+, encoding/json runs on the new v2 implementation (same behavior, different error text), and encoding/json/v2 adds stricter defaults such as rejecting duplicate keys.

JavaScript's JSON.stringify includes every enumerable property; Go includes only exported fields.

The default HTTP client never times out

http.Get uses http.DefaultClient, which has no timeout. Create &http.Client{Timeout: 10 * time.Second} or pass a context with a deadline, and set ReadHeaderTimeout on servers. Always close response bodies (defer resp.Body.Close()).

Many HTTP clients in other languages also default to no timeout. Long-running Go services make it matter more.

Equality has sharp edges

Slices, maps and functions can't be compared with == (use slices.Equal, maps.Equal). Structs compare field by field if every field is comparable. Comparing two interfaces holding slices panics at runtime. time.Time should be compared with t.Equal(u), because == also compares location and monotonic clock data.

Java splits reference == from equals(), and JavaScript compares objects by reference. Go's == compares values.

defer runs at function end, with arguments fixed early

defer f.Close() inside a loop keeps every file open until the function returns, and defer log.Println(time.Since(start)) evaluates time.Since immediately. Wrap the body in a function, or defer a closure: defer func() { log.Println(time.Since(start)) }().

Python's with and Java's try-with-resources clean up at the end of a block; defer waits for the function to return.

Unused imports and variables don't compile

Commenting out a line can break the build. Assign to _ while sketching, and let goimports or gopls manage imports.

Most other toolchains report these as warnings.

Reach for it when

  • go vet and staticcheck in CI: they catch copied locks, bad format verbs, shadowing hazards and more.
  • -race on every test run.
  • Explicit units: 5 * time.Second, never bare numbers.
  • utf8 and []rune whenever "character" matters.
  • Reading the go line in go.mod before trusting loop semantics in old code.

Watch out for

  • Assuming a value is shared when Go copied it, or copied when a slice shares it.
  • Relying on map order, unbounded HTTP calls, or JSON fields you forgot to export.
  • Recovering panics as a substitute for error handling.
  • Mixing up len in bytes with length in characters.
  • Treating nil interface checks as cheap null checks.

A small JSON API with only the standard library

main.go
package main

import (
	"encoding/json"
	"errors"
	"log/slog"
	"net/http"
	"os"
	"strconv"
	"time"
)

type Item struct {
	ID    int       `json:"id"`
	Name  string    `json:"name"`
	Added time.Time `json:"added,omitzero"`
}

func main() {
	slog.SetDefault(slog.New(slog.NewJSONHandler(os.Stderr, nil)))

	mux := http.NewServeMux()
	mux.HandleFunc("GET /items/{id}", getItem) // method + wildcard, Go 1.22+
	mux.HandleFunc("POST /items", createItem)

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           mux,
		ReadHeaderTimeout: 5 * time.Second, // always set server timeouts
	}
	slog.Info("listening", "addr", srv.Addr)
	if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
		slog.Error("server stopped", "err", err)
		os.Exit(1)
	}
}

func getItem(w http.ResponseWriter, r *http.Request) {
	id, err := strconv.Atoi(r.PathValue("id"))
	if err != nil {
		http.Error(w, "id must be a number", http.StatusBadRequest)
		return
	}
	writeJSON(w, http.StatusOK, Item{ID: id, Name: "widget", Added: time.Now()})
}

func createItem(w http.ResponseWriter, r *http.Request) {
	var in Item
	body := http.MaxBytesReader(w, r.Body, 1<<20) // cap request size at 1 MiB
	if err := json.NewDecoder(body).Decode(&in); err != nil {
		http.Error(w, "invalid JSON: "+err.Error(), http.StatusBadRequest)
		return
	}
	in.Added = time.Now()
	writeJSON(w, http.StatusCreated, in)
}

func writeJSON(w http.ResponseWriter, status int, v any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	if err := json.NewEncoder(w).Encode(v); err != nil {
		slog.Error("encode response", "err", err)
	}
}

2. The checker package

// Package check probes URLs concurrently and reports their status.
package check

import (
	"context"
	"errors"
	"fmt"
	"net/http"
	"sync"
	"time"
)

// ErrBadStatus marks responses with a 4xx or 5xx status.
var ErrBadStatus = errors.New("bad status")

// Result is the outcome of checking one URL.
type Result struct {
	URL     string        `json:"url"`
	Status  int           `json:"status,omitzero"`
	Latency time.Duration `json:"latency_ns"`
	Err     string        `json:"error,omitempty"`
}

// OK reports whether the URL answered without error.
func (r Result) OK() bool { return r.Err == "" }

// Doer is the one method of *http.Client the checker needs.
// Declaring it here, at the consumer, makes testing trivial.
type Doer interface {
	Do(*http.Request) (*http.Response, error)
}

// Checker checks URLs with bounded concurrency. Create one with New.
type Checker struct {
	Client      Doer
	Concurrency int
	Timeout     time.Duration
}

// New returns a Checker with sensible defaults. A nil client uses a fresh http.Client.
func New(client Doer) *Checker {
	if client == nil {
		client = &http.Client{}
	}
	return &Checker{Client: client, Concurrency: 8, Timeout: 5 * time.Second}
}

// Check probes every URL and returns results in input order.
func (c *Checker) Check(ctx context.Context, urls []string) []Result {
	results := make([]Result, len(urls))
	sem := make(chan struct{}, max(c.Concurrency, 1)) // a counting semaphore
	var wg sync.WaitGroup
	for i, u := range urls {
		wg.Go(func() { // Go 1.25+
			select {
			case sem <- struct{}{}: // take a slot
				defer func() { <-sem }() // give it back
			case <-ctx.Done(): // cancelled while waiting (Ctrl-C)
				results[i] = Result{URL: u, Err: ctx.Err().Error()}
				return
			}
			results[i] = c.checkOne(ctx, u) // distinct index per goroutine: no race
		})
	}
	wg.Wait()
	return results
}

func (c *Checker) checkOne(ctx context.Context, url string) Result {
	ctx, cancel := context.WithTimeout(ctx, c.Timeout)
	defer cancel()

	start := time.Now()
	status, err := c.fetch(ctx, url)
	res := Result{URL: url, Status: status, Latency: time.Since(start)}
	if err != nil {
		res.Err = err.Error()
	}
	return res
}

func (c *Checker) fetch(ctx context.Context, url string) (int, error) {
	req, err := http.NewRequestWithContext(ctx, http.MethodHead, url, nil)
	if err != nil {
		return 0, fmt.Errorf("build request: %w", err)
	}
	resp, err := c.Client.Do(req)
	if err != nil {
		return 0, fmt.Errorf("head %s: %w", url, err)
	}
	defer resp.Body.Close()
	if resp.StatusCode >= 400 {
		return resp.StatusCode, fmt.Errorf("%w: %d", ErrBadStatus, resp.StatusCode)
	}
	return resp.StatusCode, nil
}

package main

import (
	"bufio"

	"encoding/json"

	"flag"

	"os/signal"

	"time"

	"example.com/urlcheck/internal/check"
)

func main() {
	if err := run(os.Args[1:]); err != nil {
		fmt.Fprintln(os.Stderr, "urlcheck:", err)
		os.Exit(1)
	}
}

// run holds the real logic so it can return errors (and be tested) instead of exiting.
func run(args []string) error {
	fs := flag.NewFlagSet("urlcheck", flag.ContinueOnError)
	file := fs.String("f", "", "read URLs from `file`, one per line")
	conc := fs.Int("c", 8, "maximum concurrent requests")
	timeout := fs.Duration("t", 5*time.Second, "per-request timeout")
	asJSON := fs.Bool("json", false, "print JSON instead of a table")
	verbose := fs.Bool("v", false, "log progress to stderr")
	if err := fs.Parse(args); err != nil {
		return err
	}
	if *verbose {
		slog.SetLogLoggerLevel(slog.LevelDebug)
	}

	urls, err := collectURLs(*file, fs.Args())
	if err != nil {
		return err
	}
	if len(urls) == 0 {
		return errors.New("no URLs given (pass them as arguments or with -f)")
	}

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
	defer stop()

	c := check.New(nil)
	c.Concurrency, c.Timeout = *conc, *timeout
	slog.Debug("checking", "urls", len(urls), "concurrency", *conc, "timeout", *timeout)

	results := c.Check(ctx, urls)

	if *asJSON {
		enc := json.NewEncoder(os.Stdout)
		enc.SetIndent("", "  ")
		if err := enc.Encode(results); err != nil {
			return fmt.Errorf("write JSON: %w", err)
		}
	} else {
		printTable(results)
	}

	failed := 0
	for _, r := range results {
		if !r.OK() {
			failed++
		}
	}
	if failed > 0 {
		return fmt.Errorf("%d of %d URLs failed", failed, len(results))
	}
	return nil
}

func collectURLs(path string, args []string) ([]string, error) {
	if path == "" {
		return args, nil
	}
	f, err := os.Open(path)
	if err != nil {
		return nil, err // *fs.PathError already says "open urls.txt: no such file…"
	}
	defer f.Close()

	var urls []string
	sc := bufio.NewScanner(f)
	for sc.Scan() {
		line := strings.TrimSpace(sc.Text())
		if line == "" || strings.HasPrefix(line, "#") {
			continue
		}
		urls = append(urls, line)
	}
	return urls, sc.Err()
}

func printTable(results []check.Result) {
	w := tabwriter.NewWriter(os.Stdout, 0, 0, 2, ' ', 0)
	defer w.Flush()
	fmt.Fprintln(w, "STATUS\tLATENCY\tURL\tERROR")
	for _, r := range results {
		status := "-"
		if r.Status != 0 {
			status = strconv.Itoa(r.Status)
		}
		fmt.Fprintf(w, "%s\t%v\t%s\t%s\n", status, r.Latency.Round(time.Millisecond), r.URL, r.Err)
	}
}

package check

import (
	"errors"
	"net/http"
	"net/http/httptest"
	"testing"
	"time"
)

func newTestServer(t *testing.T) *httptest.Server {
	t.Helper()
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		switch r.URL.Path {
		case "/ok":
			w.WriteHeader(http.StatusOK)
		case "/slow":
			time.Sleep(200 * time.Millisecond)
		default:
			http.NotFound(w, r)
		}
	}))
	t.Cleanup(srv.Close)
	return srv
}

func TestCheck(t *testing.T) {
	srv := newTestServer(t)
	c := New(srv.Client())
	c.Timeout = 50 * time.Millisecond

	tests := []struct {
		name   string
		path   string
		wantOK bool
	}{
		{"ok", "/ok", true},
		{"not found", "/missing", false},
		{"timeout", "/slow", false},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got := c.Check(t.Context(), []string{srv.URL + tt.path})[0]
			if got.OK() != tt.wantOK {
				t.Errorf("OK() = %v, want %v (result %+v)", got.OK(), tt.wantOK, got)
			}
		})
	}
}

func TestFetchWrapsBadStatus(t *testing.T) {
	srv := newTestServer(t)
	c := New(srv.Client())

	_, err := c.fetch(t.Context(), srv.URL+"/missing")
	if !errors.Is(err, ErrBadStatus) {
		t.Fatalf("fetch error = %v, want it to wrap ErrBadStatus", err)
	}
}

func TestCheckKeepsOrder(t *testing.T) {
	srv := newTestServer(t)
	c := New(srv.Client())
	urls := []string{srv.URL + "/missing", srv.URL + "/ok", srv.URL + "/missing"}

	got := c.Check(t.Context(), urls)
	for i, r := range got {
		if r.URL != urls[i] {
			t.Errorf("result %d is for %s, want %s", i, r.URL, urls[i])
		}
	}
}

Ideas for extending it: retry with backoff on 5xx, fall back to GET when a server rejects HEAD, read URLs from stdin, or add a -serve flag that exposes the last results over HTTP with the stdlib router.

Reach for it when

  • Keeping main thin: parse flags, call run, map the error to an exit code.
  • Writing results by index so goroutines never share a slot.
  • Giving every network call a context with a timeout.
  • Testing against httptest.NewServer rather than the real internet.

Watch out for

  • Calling os.Exit deep inside the program; deferred calls won't run.
  • Unbounded fan-out: one goroutine per URL is fine, one request per URL at once is not.
  • Forgetting defer cancel() after context.WithTimeout; go vet flags it.
  • Using HEAD blindly; some servers answer it with 405.
