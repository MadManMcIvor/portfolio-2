JavaScript and TypeScript: a working reference

A quick-reference guide for programmers who already know at least one language. It covers how JavaScript and TypeScript work underneath, what changed in recent versions, and where they behave differently from other mainstream languages. Comparisons use Python, Java and Go as reference points, with equivalent code side by side.

Blue is the type layer. It exists only at compile time and is erased before the code runs. Yellow marks what is running right now in the step-throughs.

This is literally what node app.ts and the TypeScript compiler do: delete the blue parts and run the JavaScript that is left. Nothing about types survives to runtime. The switch applies to every TypeScript snippet on the page, and the copy buttons copy whichever version you are looking at.

Philosophy, trade-offs, and where it's used

JavaScript is a dynamic language that can never break old code, because the web would break with it. TypeScript is a static type checker that describes that JavaScript without changing what it does at runtime.

The idea in plain words

JavaScript was built in 1995 to script web pages. Its core design is small: dynamic types, first-class functions, objects that inherit from other objects (prototypes), and a single thread driven by an event loop. Everything since has been added on top through the ECMAScript standard, which TC39 publishes yearly. A feature lands in an edition once it reaches Stage 4, and engines like V8 (Chrome, Node, Deno), JavaScriptCore (Safari, Bun) and SpiderMonkey (Firefox) usually ship it before the edition is final.

The rule that explains most of JavaScript's quirks is "don't break the web". Bad decisions from 1995, like == coercion or typeof null === "object", can never be removed, only made avoidable with new syntax (===, let, classes, modules). Compare Python 3, which broke Python 2 code to fix the language; JavaScript will never have that moment.

TypeScript adds a type system on top. Its design goals matter because they explain its behavior:

  • Types are erased. There is no runtime type information. You cannot ask "is this a User?" at runtime the way Java's instanceof works on interfaces. You check shapes yourself or with a validation library.
  • Structural, not nominal. A value is a User if it has the right shape, like Go interfaces but applied to every type, not just interfaces.
  • Deliberately unsound. The type system is designed to describe real-world JavaScript idioms, and soundness was an explicit non-goal. A few holes are left open on purpose (more under Syntax and Gotchas).
  • Gradual. any lets typed and untyped code mix, which is how huge JS codebases migrated.

What changed recently

TypeScript 7.0 (July 2026) is the compiler and language server ported from TypeScript to Go. The type-checking logic was ported structurally, so semantics match 6.0, but builds are roughly ten times faster and checking runs in parallel. TypeScript 6.0 (March 2026) was the bridge release that turned on modern defaults such as strict and ESM output and removed legacy options. Separately, Node.js can now run .ts files directly by stripping types, and Node 26 brought the Temporal date API as a stable global.

Real-world examples

  • Front end: essentially every web UI: React, Vue, Svelte, Angular, plus frameworks like Next.js and Astro.
  • Back end: HTTP APIs with Fastify, Hono, Express or NestJS; BFF (backend-for-frontend) layers; GraphQL servers.
  • Edge and serverless: Cloudflare Workers, Vercel and Netlify functions, AWS Lambda; V8 isolates start in milliseconds.
  • Desktop and mobile: VS Code, Slack and Discord desktop (Electron); React Native apps.
  • Infrastructure as code: AWS CDK and Pulumi programs are commonly written in TypeScript.

Reach for it when

  • The work touches a browser, or shares types between front and back end
  • The service is I/O-bound: APIs, proxies, glue, webhooks
  • You need fast cold starts at the edge

Watch out for

  • CPU-bound number crunching (reach for Go, Rust or a worker pool)
  • Assuming types protect you from bad input at runtime; they don't
  • Blindly adding dependencies for small utilities

Toolchain

The runtime runs JavaScript; the TypeScript compiler only checks types. Since 2025, running and checking are fully separate steps, which is a big shift for anyone used to compiled languages like Java or Go.

The idea in plain words

In Go, go build type-checks and compiles in one step and won't produce a binary from broken code. In TypeScript, the program runs fine even if it has type errors, because the runtime simply deletes the types. Type checking is a separate gate you run in your editor and CI, much like running mypy on Python code.

Install and run

Type stripping caveat: node file.ts only works for erasable syntax: annotations, interfaces, type aliases, generics. Features that generate runtime code, such as enum, namespace and constructor parameter properties, are rejected. Set "erasableSyntaxOnly": true so the compiler flags them for you. If you need those features, use tsx, Bun or Deno, which transpile everything.

Syntax essentials and the type system

Runtime JavaScript has eight value types. TypeScript layers a structural, set-based type system on top, where types describe which values are allowed and narrowing follows your control flow.

Declarations and scope

Variables are declared with let and constants with const. A const binding can't be reassigned, but if it holds an object, that object can still be changed, so const behaves like Java's final rather than a true constant. Both are block-scoped (visible only inside the nearest { }) and can't be read before the line that declares them. The older var is function-scoped and hoisted, meaning it exists as undefined before its declaration; modern code doesn't use it. Convention is const by default and let only when the value is reassigned.

Naming is camelCase for variables and functions and PascalCase for classes and types; UPPER_SNAKE_CASE is sometimes used for module-level constants. In TypeScript, a type annotation goes after the name (let count: number = 0) and is usually left off when the type can be inferred from the value.

Statements and control flow

The statement syntax is C-family, like Java and Go: braces for blocks, if/else, switch, for, while, do…while, the ternary a ? b : c, and // and /* */ comments. Semicolons are technically optional because the parser inserts them automatically, but most style guides and formatters include them. switch falls through between cases unless you break or return, unlike Go.

Runtime values

Seven primitives, all immutable and copied by value: number (always a 64-bit float, like Python's float; there is no int), bigint (10n, arbitrary precision like Python's int), string (immutable, UTF-16), boolean, undefined, null, and symbol. Everything else is an object, including arrays, functions, dates and maps.

Two "nothing" values exist: undefined means "never set" (missing property, missing argument, function with no return), and null means "deliberately empty". Python and Java have one; Go uses zero values instead. Most modern code treats them together using ?. and ??.

Types as sets of values

The most useful mental model: a TypeScript type is the set of values it allows. string is every string, "admin" is a set with one value, "admin" | "member" is the union of two sets, unknown is every value, and never is the empty set. Assignability means "is this set a subset of that one". Because sets are judged by contents, two differently named types with the same shape are the same type. That's structural typing, and it's the biggest difference from Java.

Narrowing: types that follow control flow

A variable's type changes as the checker learns more from your if, typeof, in, instanceof, equality checks and early returns. The idiomatic way to model "one of several shapes" is a discriminated union: every member has a literal tag field, and switching on the tag narrows to that member. It replaces class hierarchies and visitor patterns in a lot of TypeScript code.

What's different and why: Java and Python dispatch on a runtime class. TypeScript can't, because types are erased, so the tag is an ordinary string property that exists at runtime. The never trick gives you Java's exhaustiveness checking; Go has none without a linter.

Where the type system is unsound on purpose

  • as assertions and ! (non-null assertion) are unchecked promises to the compiler.
  • Arrays are covariant: a Dog[] can be passed where Animal[] is expected and then have a Cat pushed into it. Java throws ArrayStoreException at runtime here; TypeScript says nothing.
  • Without noUncheckedIndexedAccess, arr[99] is typed as T, not T | undefined.
  • Data from JSON.parse, fetch and other I/O is only as typed as you claim it is. Validate at the boundary (with Zod, Valibot or hand-written guards).

Reach for it when

  • Literal unions instead of enum
  • Discriminated unions for state machines, API results and events
  • satisfies for config objects you want checked but precisely inferred
  • unknown at every untrusted boundary

Watch out for

  • || when you mean ??: 0 || 8080 is 8080
  • for…in on arrays (string keys, inherited props)
  • Treating an interface as a runtime check; nothing exists to check against
  • Excess-property checks only apply to fresh object literals, not variables

Collections and data structures

Arrays, plain objects, Map and Set cover nearly everything. The standard library has no heap, deque, sorted map or linked list.

The idea in plain words

An Array is a growable list like Python's list or Java's ArrayList. A plain object {} is a string-keyed record; use it for fixed shapes known at compile time. A Map is a real hash map: any key type (including objects, compared by identity), insertion-ordered, with .size, and no inherited keys like "constructor" to collide with. Use Map whenever keys come from data. Set is a hash set with insertion order and, since ES2025, real set algebra.

Recent additions worth knowing: non-mutating array methods (toSorted, toReversed, toSpliced, with), Object.groupBy/Map.groupBy, Set methods (union, intersection, difference, isSubsetOf), lazy iterator helpers (.map, .filter, .take directly on iterators), and in Node 26, Map.prototype.getOrInsert/getOrInsertComputed and Iterator.concat.

Functions, closures, and generics

Functions are ordinary values that remember the variables around them. Generics are inferred, structural, and erased, so they constrain shapes, not runtime classes.

The idea in plain words

There are two common forms. A function declaration is hoisted (usable before its line) and gets its own this. An arrow function (x) => x + 1 is not hoisted and inherits this from where it was written, which is why arrows are the default for callbacks. Neither form supports overloading by parameter type the way Java does; TypeScript offers overload signatures over a single implementation.

There are no keyword arguments. The idiom for Python-style named arguments is to pass one options object and destructure it, which also gives you defaults and makes call sites self-describing.

A closure captures variables, not values. Every function holds a reference to the scope it was created in, and it sees later changes to those variables. Go 1.22 fixed the classic loop-variable bug by giving each iteration a fresh variable; JavaScript's let did the same thing in 2015, while var still has the old behavior.

Generics

Type parameters are almost always inferred from arguments. Constraints use extends to say "at least this shape". Because generics are erased, like Java's but unlike Go's, you can't write new T() or check x instanceof T; pass a constructor or a validator function instead. TypeScript's generics go further than Java's or Go's: keyof, indexed access T[K], mapped types and conditional types let you compute types from other types.

What's different and why: TypeScript can type a variadic function generically (A extends unknown[]), like Python's ParamSpec. But there's no hashCode/comparable, so object arguments need an explicit key (here JSON), because Map compares objects by identity.

Reach for it when

  • Arrow functions for callbacks and anything that uses this from outside
  • Options objects once a function has more than two parameters
  • Closures for small private state instead of a class
  • Generic constraints over any

Watch out for

  • ["1","2","3"].map(parseInt) is [1, NaN, NaN]: map passes (value, index)
  • Default parameters are evaluated per call (unlike Python's shared mutable default)
  • Type-level cleverness that nobody can read; prefer a few overloads
  • Closures in long-lived listeners keep big objects alive

Error handling

Exceptions, unchecked, untyped, and able to carry any value. TypeScript doesn't track what a function throws, so errors you expect callers to handle are often better returned as values.

The idea in plain words

throw accepts anything (throw "oops" is legal), so the caught value is typed unknown under strict. Always throw Error objects (they carry a stack trace) and narrow before using the caught value. There are no checked exceptions like Java's and no throws clause in types. Async code reports errors as rejected promises; await turns a rejection back into a throw, so try/catch works across async code the way it does in Python's asyncio.

Two modern tools: the cause option chains errors (like Java's cause or Go's %w wrapping), and using declarations run cleanup automatically when a block exits, like Python's with, Java's try-with-resources, or Go's defer. using is supported in Node 24+ and TypeScript.

You'll often see the shorter constructor(public readonly key: string) form, called a parameter property, in Angular and NestJS code. It generates runtime code, so it isn't erasable and node file.ts rejects it. With erasableSyntaxOnly, declare the field and assign it in the constructor, as above.

What's different and why: you can't have several typed catch clauses as in Java or Python; there is one catch and you branch with instanceof or by checking .code. Node's system errors are identified by a string code such as ENOENT, not by subclass.

Reach for it when

  • Exceptions for bugs and truly exceptional failures
  • Result unions for expected outcomes (validation, "not found", parse failures)
  • { cause } every time you rethrow
  • using/await using for locks, handles and temp files

Watch out for

  • Floating promises: an un-awaited rejected promise crashes Node with an unhandled rejection. Enable the no-floating-promises lint rule
  • catch (e) { console.log(e.message) } on unknown won't compile, and shouldn't
  • Errors thrown inside setTimeout callbacks escape your try
  • Swallowing errors with an empty catch {}

Objects and code reuse

Objects are dictionaries that delegate missing lookups to another object, their prototype. Classes are syntax over that chain. Interfaces are structural and satisfied implicitly, like Go.

The idea in plain words

When you read obj.x and obj has no own property x, the engine asks obj's prototype, then that object's prototype, until it reaches null. Methods defined in a class live once on ClassName.prototype and are shared by every instance. extends just links one prototype to another. This is closer to Python's attribute lookup through the MRO than to Java's vtables, but with single inheritance only.

Interfaces describe shapes and exist only at compile time. A class doesn't need to declare implements to satisfy one; implements is just an early check. That's Go's model: any value with the right members fits.

Code reuse without deep hierarchies

Idiomatic modern TypeScript uses few classes. Reuse comes from plain functions, composition (an object holding collaborators), and interfaces for contracts. When you want trait-like shared behavior, a mixin is a function that takes a class and returns a subclass. In front-end code, React hooks or Vue composables play the same role.

What's different and why: the TypeScript version needs no class and no lock. Structural typing means the returned object literal is a Store because of its shape, and single-threaded execution means the map can't be corrupted by concurrent writes (though two concurrent gets for the same key will both fetch).

Reach for it when

  • Classes for things with identity and lifecycle (connections, caches, domain entities); also for custom errors
  • #private when privacy must hold at runtime (libraries)
  • Interfaces for contracts between modules
  • Composition and functions before inheritance

Watch out for

  • Passing obj.method as a callback loses this (see Gotchas)
  • TS private is not real privacy
  • Class instances don't survive JSON round-trips; you get plain objects back
  • Java-style deep hierarchies and getters/setters for everything

Concurrency model

One thread runs your code, one task at a time, each to completion. Concurrency comes from non-blocking I/O and an event loop; parallelism comes from separate workers that share nothing by default.

The idea in plain words

The engine has a call stack and two waiting lines. When the stack empties, it drains the entire microtask queue (promise callbacks and the code after each await), then takes one task (timer, I/O completion, incoming request) from the task queue, runs it, drains microtasks again, and repeats. Nothing ever interrupts running code, so there are no data races on ordinary variables and no need for locks. But anything that holds the thread, like a long loop or JSON.parse on a 200 MB string, freezes every other request or the whole UI.

Compared with other languages: it resembles Python's asyncio, except the loop always exists, almost every I/O API is async, and there's no GIL story because there's only one thread to begin with. It is not Go: goroutines are preemptively scheduled across all cores; JavaScript tasks are cooperative on one core. Logical races still exist, because state can change between two awaits.

Real parallelism

For CPU-heavy work, use worker threads (node:worker_threads on the server, Web Workers in browsers). Each worker is a separate isolate with its own heap and event loop. They communicate by message passing, which copies data using the structured clone algorithm. That's similar to Go channels in spirit, but much heavier: no shared memory unless you opt into SharedArrayBuffer with Atomics. In production you'd use a pool (such as Piscina) rather than spawning a worker per job.

What's different and why: next++ needs no lock or atomic in JavaScript because nothing can run between reading and writing it; the only switch points are awaits. In Go and Java the same counter would be a data race. But the JS version only helps with I/O waits; it never uses a second core.

Reach for it when

  • Promise.all for independent I/O, allSettled when partial failure is fine
  • AbortSignal for timeouts and cancellation, passed down like Go's context
  • Worker threads for image processing, parsing, crypto, compression

Watch out for

  • await inside a for loop when the calls are independent (accidentally sequential)
  • array.forEach(async …) doesn't wait for anything
  • Unbounded Promise.all over 10,000 items: you'll exhaust sockets or rate limits
  • Sync APIs (readFileSync, heavy loops) in request handlers
  • Promises can't be cancelled themselves; only work that listens to a signal stops

Memory model

Garbage collected. Primitives behave like values; every object is reached through a reference, and assignment or argument passing copies the reference, never the object.

The idea in plain words

This is the same model as Python and Java (for objects): "call by sharing". A function can mutate an object you pass it, but reassigning its parameter doesn't affect your variable. There are no pointers, no &, and no value-type structs, which is the big difference from Go, where assigning a struct copies it. If you need a copy, you make one: spread for a shallow copy, structuredClone for a deep one.

V8's collector is generational and mostly concurrent. Short-lived objects are allocated in a small young generation and cleared cheaply; survivors are promoted to the old generation, which is marked and compacted incrementally. An object is collected when nothing reachable from the roots (globals, the stack, active closures, pending callbacks) refers to it. You never free memory, but you can leak it by staying reachable.

What's different and why: in Go you choose between value and pointer at every use site. In JavaScript every object is effectively always behind a pointer, so the question is only "do I need a copy?" Immutability-by-convention (never mutate shared data, return new objects) is how JS code avoids aliasing bugs.

How memory leaks happen

  • Module-level Map caches with no eviction; they grow forever on a server.
  • Event listeners and intervals that are never removed, keeping their closures (and everything those capture) reachable.
  • Closures that capture a large object when they need only one field.
  • In browsers, references to DOM nodes that have been removed from the page.

Tools: process.memoryUsage(), heap snapshots in Chrome DevTools (compare two snapshots and sort by "retained size"), and --max-old-space-size to raise Node's heap ceiling. For caches keyed by objects, WeakMap lets entries disappear with their keys; WeakRef and FinalizationRegistry exist but are rarely the right tool.

Reach for it when

  • structuredClone for deep copies of plain data
  • Spread plus immutable updates for state
  • WeakMap for per-object metadata
  • An LRU with a size bound for every server-side cache

Watch out for

  • Spread is shallow: nested arrays and objects are still shared
  • const means the binding can't change, not that the object is immutable
  • Object.freeze is shallow too
  • readonly in TypeScript is compile-time only

Modules, packages, and visibility

Each file is a module. Anything not exported is private to that file. A package's public surface is whatever its package.json "exports" field allows.

The idea in plain words

Modern code uses ES modules: import/export, static and analyzable, loaded once and cached, with top-level await allowed. The older CommonJS format (require, module.exports) still fills npm. Current Node versions can require() an ES module as long as it has no top-level await, which has removed most of the old interop pain. Set "type": "module" and write ESM.

Visibility has two levels. Inside a package, the unit is the file: export it or it's private, which is coarser than Java's four levels and differs from Go's package-wide visibility with capitalization. Across packages, the "exports" map in package.json lists the entry points consumers may import; everything else is blocked, which works like Go's internal/ directories or Java's module-info exports.

Version ranges: ^7.0.0 means any 7.x (compatible minor and patch updates), ~7.0.0 means 7.0.x only. The lockfile pins exact versions. peerDependencies says "the app must supply this", which is how plugins avoid bundling a second copy of React. Published libraries ship compiled .js plus .d.ts declaration files; Node refuses to strip types from files inside node_modules.

Idiomatic style

Good modern TypeScript reads like typed, mostly functional JavaScript: small modules of functions over plain data, types at the boundaries, inference everywhere else.

What good looks like

  • Annotate boundaries, infer the middle. Type parameters and exported return types; let locals infer. Over-annotation is the Java habit to drop.
  • Model data as types, not classes. Plain objects described by type/interface, and discriminated unions for variants.
  • Make illegal states unrepresentable. { status: "loading" } | { status: "ok"; data: T } beats { loading: boolean; data?: T; error?: string }.
  • Don't mutate what you didn't create. Return new arrays and objects; mutate freely inside a function's own locals.
  • Validate untrusted data once, at the edge, then trust the types inside.
  • async/await, not .then chains; early returns over nesting; const everywhere you can.
What changed: no class wrapping stateless logic, no any, no var/for…in/==, inferred return type, and the data source is a parameter, which makes it trivially testable.

Gotchas

Common surprises, especially for developers who know Python, Java or Go. Most come from coercion, floating-point numbers, this, and the fact that types disappear at runtime.

this depends on the call, not the definition

In Python, obj.method is a bound method you can pass anywhere. In Java, this is always the instance. In JavaScript, this is whatever is to the left of the dot at the call site. Pass the method alone and the receiver is gone.

Reach for it when

  • === always; == null is the one accepted exception (matches null and undefined)
  • Number.isNaN, Number.parseInt(s, 10)
  • Lint rules: eqeqeq, no-floating-promises, unbound-method

Watch out for

  • parseInt("08abc") is 8; Number("08abc") is NaN

End-to-end project: a concurrent link checker

A small CLI that reads a list of URLs, checks them with bounded concurrency and per-request timeouts, prints a report, and sets a failing exit code. It runs with plain node, has zero runtime dependencies, and its tests use only the built-in runner.

It ties together most of the guide: ES modules and visibility, a discriminated union for results, errors converted to values at the boundary, generics, async/await with a concurrency limit, AbortSignal.timeout, built-in parseArgs and styleText, and node:test with a real local HTTP server. This exact code was run and type-checked with strict settings before being included.

linkcheck/ ├── package.json ├── tsconfig.json the strict config from the Toolchain topic ├── src/ │ ├── check.ts pure logic: parse, check, limit concurrency │ └── main.ts CLI: args, file I/O, output, exit code └── test/ └── check.test.ts
Things to notice: check.ts has no I/O besides fetch, which is injectable, so it tests without mocks. checkUrl never throws, so one bad URL can't reject the whole Promise.all. noUncheckedIndexedAccess is why the code says positionals[0] might be undefined and why items[i]! needs the assertion. Try the Erase types switch on these files: what remains is the JavaScript Node actually runs.

Ways to extend it

  • Retry failed checks with exponential backoff, and test it with an injected fetchFn.
  • Move the CPU-light checks into a worker pool and compare the timing (it shouldn't help: this is I/O-bound).
  • Add a --watch mode with fs.watch and an AbortController that cancels the in-flight run when the file changes.
  • Validate a JSON config file with Zod and infer CheckOptions from the schema.
