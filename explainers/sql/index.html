SQL, the way the database reads it

You write a query top to bottom, but the database evaluates it in a different order. Most confusing errors make sense once you see that order.

Each number is the step in which that clause runs.

  1. 5SELECT city, count(*) AS orders, sum(total) AS revenueCompute the output columns and give them names. Aliases like revenue are born here.
  2. 1FROM ordersStart with every row of orders.
  3. 1JOIN customers ON customers.id = orders.customer_idPair each order with its customer. The result is one wide table.
  4. 2WHERE ordered_on >= '2024-01-01'Throw away rows before grouping. The SELECT aliases don’t exist yet, so WHERE revenue > 100 fails.
  5. 3GROUP BY cityCollapse the surviving rows into one row per city.
  6. 4HAVING count(*) > 2Filter the groups. Aggregates like count(*) only work from this point on.
  7. 6ORDER BY revenue DESCSort the finished result. revenue exists now, so the alias works.
  8. 7LIMIT 5;Keep the first five rows. Without ORDER BY, “first” would mean nothing.

DuckDB and SQLite bend this rule and let you use a SELECT alias in WHERE. Postgres follows it strictly. Writing queries as if the rule holds everywhere keeps them portable.

The rest of this page covers the language itself, then the places where Postgres, DuckDB and SQLite disagree. Pick your database at the top, and every dialect-specific example switches with you. Examples use a small two-table shop you can create in the next section.

The mental model

A table is a set of rows, and every row has the same columns. “Set” matters: rows have no built-in order. If you don’t say ORDER BY, the database can return them in any order it likes, and that order can change between runs.

SQL is declarative. You describe the result you want; the query planner decides how to get it, which indexes to use, and which table to read first. Two queries that look very different can run with the same plan.

Every step of a query produces another table. That’s why you can put a whole query in FROM, join to the output of a CTE, or wrap a query in another query. If you can picture the intermediate table at each step from the card above, you can debug almost anything.

A primary key uniquely identifies a row. A foreign key is a column that holds another table’s primary key, which is how tables point at each other. Joins follow those pointers.

The sample data

This script runs unchanged in all three databases. Paste it into a fresh database and every example below will work.

CREATE TABLE customers (
  id      INTEGER PRIMARY KEY,
  name    TEXT NOT NULL,
  city    TEXT,
  joined  DATE NOT NULL
);

CREATE TABLE orders (
  id           INTEGER PRIMARY KEY,
  customer_id  INTEGER REFERENCES customers(id),
  ordered_on   DATE NOT NULL,
  total        DECIMAL(10,2) NOT NULL
);

INSERT INTO customers VALUES
  (1, 'Ana',   'Lisbon', '2023-03-14'),
  (2, 'Bilal', 'Leeds',  '2023-07-02'),
  (3, 'Chen',  'Lisbon', '2024-01-20'),
  (4, 'Dara',  NULL,     '2024-02-11');

INSERT INTO orders VALUES
  (10, 1,    '2024-01-05', 42.50),
  (11, 1,    '2024-02-17', 18.00),
  (12, 2,    '2024-02-20', 99.90),
  (13, 3,    '2024-03-02', 12.25),
  (14, 1,    '2024-03-09', 65.00),
  (15, NULL, '2024-03-10', 30.00);

Dara has no orders, and order 15 has no customer. Both are there on purpose: they’re what make joins and NULLs interesting.

Reading rows

SELECT name, city
FROM customers
WHERE city = 'Lisbon'
ORDER BY name
LIMIT 10;

Strings use single quotes: 'Lisbon'. Double quotes are for identifiers, such as a column called "Order Date" with a space in it. Mixing them up is the most common first-day error.

WHERE takes any true-or-false expression. Combine conditions with AND, OR and NOT, and use parentheses when you mix AND with OR, because AND binds tighter.

SELECT
  name,
  CASE WHEN joined < '2024-01-01' THEN 'early' ELSE 'new' END AS cohort
FROM customers
WHERE city IN ('Lisbon', 'Leeds')      -- any of these values
  AND name LIKE 'A%'                   -- % = any run of characters, _ = one character
  AND joined BETWEEN '2023-01-01' AND '2023-12-31';  -- inclusive at both ends
  • DISTINCT removes duplicate rows from the result: SELECT DISTINCT city FROM customers.
  • AS names a column or table. FROM customers AS c lets you write c.name; the AS is optional for tables.
  • CASE is SQL’s if/else. It returns the first matching THEN, or the ELSE value, or NULL if nothing matches and there’s no ELSE.
  • LIMIT n OFFSET m skips m rows and returns n. Fine for small pages; slow for deep ones, because the database still walks the skipped rows.

NULL

NULL means “unknown”, not zero and not empty. Any comparison with an unknown is itself unknown, and WHERE only keeps rows where the condition is definitely true. So city = NULL matches nothing, not even Dara.

SELECT name FROM customers WHERE city IS NULL;        -- Dara
SELECT name, coalesce(city, 'unknown') FROM customers; -- first non-NULL argument
SELECT nullif(total, 0) FROM orders;                   -- turns 0 into NULL (handy before dividing)
ExpressionResultWhy
NULL = NULLNULLTwo unknowns aren’t known to be equal.
NULL AND falsefalseWhatever the unknown is, the whole thing is false.
NULL OR truetrueWhatever the unknown is, the whole thing is true.
NULL + 1NULLArithmetic on an unknown is unknown.
NULL IS NULLtrueIS asks “is it unknown?”, which has a definite answer.
a IS DISTINCT FROM btrue or falseLike <> but treats two NULLs as equal. Works in all three (SQLite 3.39+); SQLite also accepts a IS NOT b.

Aggregates skip NULLs: avg(x) averages only the known values, and sum of an all-NULL column is NULL, not 0.

Aggregating

GROUP BY collapses rows that share values into one row each, and aggregate functions summarise each group.

SELECT customer_id,
       count(*)        AS orders,
       sum(total)      AS spent,
       avg(total)      AS avg_order,
       max(ordered_on) AS last_order,
       count(*) FILTER (WHERE total > 50) AS big_orders
FROM orders
WHERE ordered_on >= '2024-01-01'   -- filters rows, before grouping
GROUP BY customer_id
HAVING sum(total) > 50;            -- filters groups, after grouping

The rule: every column in SELECT must either appear in GROUP BY or sit inside an aggregate. Postgres enforces it. SQLite doesn’t, and quietly picks a value from some row in the group, which can hide real bugs. DuckDB enforces it but gives you GROUP BY ALL, which groups by every non-aggregated column for you.

  • count(*) counts rows. count(col) counts rows where col isn’t NULL. count(DISTINCT col) counts different non-NULL values.
  • FILTER (WHERE …) applies a condition to one aggregate only. All three databases support it (SQLite 3.30+). The portable fallback is sum(CASE WHEN … THEN 1 ELSE 0 END).
  • NULLs form their own group. Grouping customers by city gives a row for Lisbon, one for Leeds and one for NULL.

Joins

A join combines rows from two tables by a condition, usually “this foreign key equals that primary key”. Think of it as building every pair of rows, then keeping the pairs where ON is true. The join type decides what happens to rows that found no partner.


    

  

  
Faded source rows are the ones that don’t make it into the result.

  
    
    
  • JOIN on its own means INNER JOIN. LEFT JOIN is short for LEFT OUTER JOIN.
    • 
    
  • USING (id) is shorthand for ON a.id = b.id when both columns share a name.
    • 
    
  • CROSS JOIN pairs every row with every row: 4 customers × 6 orders = 24 rows. Useful for generating combinations, dangerous by accident.
    • 
    
  • A self join joins a table to itself under two aliases, for example employees to their managers.
    • 
    
  • SQLite added RIGHT and FULL joins in version 3.39 (2022). On older versions, swap the tables and use LEFT.
    • 
  

  
Joins multiply. If a customer has three orders and three support tickets, joining both tables gives nine rows for that customer, and any sum over them is inflated. Aggregate each table first, then join the results. The gotchas section shows the fix.






  
Subqueries and CTEs

  
Because every query produces a table, you can use a query anywhere a table or value fits. A CTE (common table expression) gives that inner query a name with WITH, so you can read the logic top to bottom.

  
WITH spend AS (
  SELECT customer_id, sum(total) AS spent
  FROM orders
  WHERE customer_id IS NOT NULL
  GROUP BY customer_id
)
SELECT c.name, s.spent
FROM customers c
JOIN spend s ON s.customer_id = c.id
WHERE s.spent > (SELECT avg(spent) FROM spend);   -- scalar subquery: one value

  
    
    
  • A scalar subquery returns one value and can go anywhere a value can.
    • 
    
  • WHERE id IN (SELECT …) tests membership. WHERE EXISTS (SELECT 1 …) tests whether any row matches.
    • 
    
  • A correlated subquery refers to the outer query (like o.customer_id = c.id inside EXISTS) and conceptually runs once per outer row. Planners usually rewrite it into a join.
    • 
    
  • UNION stacks results and removes duplicates; UNION ALL keeps them and is faster. INTERSECT and EXCEPT give rows in both, or in the first but not the second.
    • 
  

  
Recursive CTEs

  
WITH RECURSIVE builds a result by repeatedly feeding it back into itself, which is how SQL walks trees (org charts, folders) and generates sequences.

  
WITH RECURSIVE n(i) AS (
  SELECT 1                              -- starting row
  UNION ALL
  SELECT i + 1 FROM n WHERE i < 10      -- repeat until this returns nothing
)
SELECT i FROM n;






  
Window functions

  
A window function computes over a group of related rows without collapsing them. GROUP BY gives one row per customer; a window gives every order its own row plus a value computed across that customer’s orders.

  
SELECT
  customer_id,
  ordered_on,
  total,
  sum(total)   OVER (PARTITION BY customer_id ORDER BY ordered_on) AS running_total,
  row_number() OVER (PARTITION BY customer_id ORDER BY ordered_on) AS nth_order,
  total - lag(total) OVER (PARTITION BY customer_id ORDER BY ordered_on) AS change
FROM orders;

  
    
    
  • PARTITION BY splits rows into independent groups. Leave it out and the whole result is one window.
    • 
    
  • ORDER BY inside OVER orders rows within each partition. It doesn’t sort the output.
    • 
    
  • row_number() numbers rows 1, 2, 3. rank() gives ties the same number and leaves gaps (1, 1, 3); dense_rank() doesn’t leave gaps (1, 1, 2).
    • 
    
  • lag(x) and lead(x) read the previous or next row. first_value, last_value and nth_value read specific positions.
    • 
    
  • A frame narrows the window: avg(total) OVER (ORDER BY ordered_on ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) is a three-row moving average.
    • 
  

  
Windows run after WHERE, GROUP BY and HAVING, so you can’t filter on them in the same query’s WHERE. To get the top order per customer:

  
SELECT *
FROM (
  SELECT o.*,
         row_number() OVER (PARTITION BY customer_id ORDER BY total DESC) AS rn
  FROM orders o
) ranked
WHERE rn = 1;

  
SELECT *
FROM orders
QUALIFY row_number() OVER (PARTITION BY customer_id ORDER BY total DESC) = 1;

  
Postgres also has DISTINCT ON for exactly this job; see your database.

  
SQLite has supported window functions since 3.25 (2018).






  
Changing data

  
INSERT INTO customers (id, name, city, joined)
VALUES (5, 'Eli', 'Leeds', '2024-04-01');

UPDATE orders SET total = total * 0.9 WHERE id = 12;

DELETE FROM orders WHERE customer_id IS NULL;

  
An UPDATE or DELETE without WHERE touches every row. Write the WHERE as a SELECT first, check the rows it returns, then swap SELECT for UPDATE or DELETE.

  
RETURNING hands back the rows you just changed, so you don’t need a second query to learn a new ID. All three support it (SQLite 3.35+): INSERT … RETURNING id.

  
Insert or update (upsert)

  
All three share the same ON CONFLICT syntax. excluded refers to the row you tried to insert.

  
INSERT INTO customers (id, name, city, joined)
VALUES (2, 'Bilal', 'York', '2023-07-02')
ON CONFLICT (id) DO UPDATE SET city = excluded.city;

-- or keep the existing row and skip the new one
INSERT INTO customers VALUES (2, 'Bilal', 'York', '2023-07-02')
ON CONFLICT DO NOTHING;

  
INSERT OR REPLACE INTO … also works here. It replaces the whole conflicting row rather than chosen columns.

  
Postgres 15 and later also support the standard MERGE statement for more complex sync logic.

  
Transactions

  
A transaction groups statements so they all happen or none do. Other sessions don’t see your changes until COMMIT.

  
BEGIN;
UPDATE orders SET total = total - 10 WHERE id = 10;
UPDATE orders SET total = total + 10 WHERE id = 12;
COMMIT;      -- or ROLLBACK; to undo both






  
Tables, types, indexes

  
Constraints are rules the database enforces for you: NOT NULL, UNIQUE, CHECK (price >= 0), PRIMARY KEY and REFERENCES. Put rules here rather than in application code, and bad data can’t get in no matter which program writes it.

  
CREATE TABLE products (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text NOT NULL UNIQUE,
  price      numeric(10,2) NOT NULL CHECK (price >= 0),
  tags       text[],
  details    jsonb,
  created_at timestamptz NOT NULL DEFAULT now()
);

  
CREATE SEQUENCE products_id_seq;

CREATE TABLE products (
  id         INTEGER PRIMARY KEY DEFAULT nextval('products_id_seq'),
  name       VARCHAR NOT NULL UNIQUE,
  price      DECIMAL(10,2) NOT NULL CHECK (price >= 0),
  tags       VARCHAR[],
  details    JSON,
  created_at TIMESTAMPTZ NOT NULL DEFAULT current_timestamp
);

  
CREATE TABLE products (
  id         INTEGER PRIMARY KEY,       -- alias for the rowid, filled in for you
  name       TEXT NOT NULL UNIQUE,
  price      REAL NOT NULL CHECK (price >= 0),
  tags       TEXT,                      -- store a JSON array as text
  details    TEXT,                      -- query with ->> or json_extract()
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
) STRICT;

PRAGMA foreign_keys = ON;   -- REFERENCES is ignored until you run this, per connection

  
Indexes

  
An index is a sorted copy of some columns that lets the database find rows without reading the whole table, like a book’s index. Index columns you filter or join on often. Each index speeds reads and slows writes a little.

  
CREATE INDEX orders_customer_idx ON orders (customer_id);
CREATE INDEX orders_date_idx     ON orders (ordered_on);

  
Check whether a query uses them with EXPLAIN ANALYZE SELECT …, which runs the query and shows the real plan and timings. Postgres also supports partial indexes (WHERE active), expression indexes (lower(email)), GIN indexes for jsonb and arrays, and full-text search.

  
DuckDB rarely needs indexes for analytics: it stores data by column and keeps min/max summaries for each chunk, so filters skip most data automatically. Indexes mainly matter for enforcing PRIMARY KEY and UNIQUE, and for point lookups. Use EXPLAIN ANALYZE to see the plan.

  
See whether SQLite uses an index with EXPLAIN QUERY PLAN SELECT …. Look for “SEARCH … USING INDEX” rather than “SCAN”. Run ANALYZE; after loading data so the planner has statistics.

  
Changing a table

  
ALTER TABLE customers ADD COLUMN email TEXT;
ALTER TABLE customers RENAME COLUMN city TO town;
DROP TABLE IF EXISTS products;

  
SQLite’s ALTER TABLE is limited: you can add, rename and (since 3.35) drop columns, but not change a column’s type or constraints. For that, create a new table, copy the rows across and rename it.

  
Postgres can change almost anything in place, for example ALTER TABLE orders ALTER COLUMN total TYPE numeric(12,2), and most schema changes are themselves transactional, so you can roll them back.

  
DuckDB supports ADD, DROP, RENAME and ALTER COLUMN … TYPE, but altering a column that has an index or constraint on it can be refused; recreating the table with CREATE TABLE new AS SELECT … is often simplest.






  
Your database


  

    
Postgres is a client–server database: a server process owns the data, and many programs connect to it over the network at once. It handles heavy concurrent reads and writes, enforces types strictly, and has a deep extension ecosystem (PostGIS for maps, pgvector for embeddings). It’s the usual choice for an application’s main database.

What Postgres does that the others don’t

    
-- Latest order per customer
SELECT DISTINCT ON (customer_id) customer_id, ordered_on, total
FROM orders
ORDER BY customer_id, ordered_on DESC;

-- One row per day in March, including days with no orders
SELECT g.d::date AS day, coalesce(sum(o.total), 0) AS revenue
FROM generate_series(timestamp '2024-03-01', timestamp '2024-03-31', interval '1 day') AS g(d)
LEFT JOIN orders o ON o.ordered_on = g.d::date
GROUP BY g.d
ORDER BY g.d;

-- jsonb: -> returns json, ->> returns text, @> tests containment
SELECT name FROM products WHERE details @> '{"color": "red"}';
SELECT details ->> 'color' FROM products;

-- Arrays
SELECT name FROM products WHERE 'sale' = ANY (tags);

    
Also worth knowing: ILIKE for case-insensitive matching, x::int as a short cast, LATERAL joins, materialized views, and schemas (namespaces inside one database).

    
What trips people up

    
    
      
  • Unquoted names are folded to lowercase. CREATE TABLE "Orders" creates a table you must always quote; Orders without quotes means orders. Stick to lowercase snake_case.
    • 
      
  • SELECT aliases can’t be used in WHERE. Repeat the expression or move it into a CTE.
    • 
      
  • Integer division truncates: 5 / 2 is 2. Write 5 / 2.0 or cast.
    • 
      
  • Types are strict. Comparing a text column with an integer is an error, not a silent conversion.
    • 
      
  • Prefer timestamptz over timestamp: it stores an absolute moment and converts to the session’s time zone for display.
    • 
    

  


  

    
DuckDB is an analytical database that runs inside your program, with no server. It stores data by column and processes it in batches, so scans and aggregates over millions of rows are fast on a laptop. It reads CSV, Parquet and JSON files directly, which makes it a strong tool for data analysis, notebooks and cleaning messy files. It isn’t meant for many programs writing at once.

In Python, duckdb.sql("SELECT * FROM df") can query a pandas or Polars DataFrame named df directly, and .df() turns any result back into one.

What trips people up

    
    
      
  • / always divides as decimals: 5 / 2 is 2.5. Use // for integer division. This differs from both Postgres and SQLite.
    • 
      
  • Only one process can open a database file for writing at a time. Several readers are fine with duckdb -readonly.
    • 
      
  • The CLI truncates long results; you’re not missing rows, they’re just hidden. Use .maxrows or LIMIT.
    • 
      
  • Names are case-insensitive but keep the case you created them with.
    • 
      
  • It’s built for bulk work. Thousands of single-row INSERTs are slow; load with COPY, read_csv or INSERT … SELECT.
    • 
    

  


  

    
SQLite is a library that keeps an entire database in one ordinary file, with no server and no setup. It ships inside phones, browsers and Python itself, and it’s one of the most widely deployed pieces of software there is. It suits app storage, local tools, tests, prototypes and small-to-medium websites. One writer at a time; readers can run alongside in WAL mode.

What SQLite does differently

    
PRAGMA foreign_keys = ON;      -- off by default, set it on every connection
PRAGMA journal_mode = WAL;     -- readers stop blocking the writer; persists in the file

-- Dates are stored as text; functions do the arithmetic
SELECT date('now'), date('now', '-7 days'), date('now', 'start of month');

SELECT strftime('%Y-%m', ordered_on) AS month, sum(total) AS revenue
FROM orders
GROUP BY month;

-- JSON lives in text columns
SELECT details ->> '$.color' FROM products;
SELECT json_extract(details, '$.size') FROM products;

-- Join strings within a group
SELECT customer_id, group_concat(id, ', ') FROM orders GROUP BY customer_id;

    
What trips people up

    
    
      
  • Column types are suggestions (“type affinity”). An INTEGER column will happily store 'abc'. Add STRICT to CREATE TABLE (3.37+) to make types real.
    • 
      
  • Foreign keys aren’t enforced until PRAGMA foreign_keys = ON, and the setting doesn’t persist.
    • 
      
  • There’s no date or boolean type. Dates are ISO text ('2024-03-09'), which sorts correctly as long as you keep the format; TRUE and FALSE are 1 and 0.
    • 
      
  • LIKE is case-insensitive for ASCII letters by default, unlike Postgres.
    • 
      
  • A double-quoted word that isn’t a column name is treated as a string, so a typo like WHERE city = "Lisbon" works here and breaks everywhere else. Use single quotes.
    • 
      
  • Integer division truncates: 5 / 2 is 2.

Gotchas


  

    
NOT IN with a NULL returns nothing

    
If the subquery contains a NULL, x NOT IN (…) is never true, because x might equal the unknown value. Our orders table has a NULL customer_id, so this returns zero rows instead of Dara.

    
-- Wrong: returns nothing
SELECT name FROM customers WHERE id NOT IN (SELECT customer_id FROM orders);

-- Right
SELECT name FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

  


  

    
A WHERE clause that undoes your LEFT JOIN

    
A condition on the right-hand table in WHERE removes the NULL rows that LEFT JOIN kept, turning it into an inner join. Put that condition in ON.

    
-- Loses Dara
SELECT c.name, o.total FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.total > 20;

-- Keeps every customer, matches only big orders
SELECT c.name, o.total FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.total > 20;

  


  

    
Joins that inflate totals

    
Joining two one-to-many tables multiplies rows, so sums count things more than once. Aggregate each side first, then join.

    
-- tickets is a hypothetical second table
WITH o AS (SELECT customer_id, sum(total) AS spent FROM orders GROUP BY customer_id),
     t AS (SELECT customer_id, count(*) AS tickets FROM tickets GROUP BY customer_id)
SELECT c.name, o.spent, t.tickets
FROM customers c
LEFT JOIN o ON o.customer_id = c.id
LEFT JOIN t ON t.customer_id = c.id;

  


  

    
Date ranges with BETWEEN

    
For timestamps, BETWEEN '2024-03-01' AND '2024-03-31' stops at midnight on the 31st and misses most of that day. Use a half-open range instead: ts >= '2024-03-01' AND ts < '2024-04-01'. It’s correct for dates and timestamps alike.

  


  

    
No ORDER BY, no order

    
Results often come back in insertion order, until the table grows, an index appears, or the query runs in parallel. LIMIT 10 without ORDER BY means “any ten rows”. If order matters, say so, and add a tie-breaker such as ORDER BY ordered_on, id.

  


  

    
Averages that are secretly integers

    
In Postgres and SQLite, sum(a) / count(*) on integer columns truncates. Multiply by 1.0 first, or use avg(). DuckDB returns a decimal either way.

Customers who joined in 2024
    
SELECT name, joined
FROM customers
WHERE joined >= '2024-01-01' AND joined < '2025-01-01';

  


  
Order count and total spent per customer, including Dara with zeros
    
SELECT c.name,
       count(o.id)               AS orders,   -- count(o.id), not count(*), so Dara gets 0
       coalesce(sum(o.total), 0) AS spent
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY spent DESC;

  


  
Cities whose customers spent more than 100 in total
    
SELECT c.city, sum(o.total) AS spent
FROM customers c
JOIN orders o ON o.customer_id = c.id
GROUP BY c.city
HAVING sum(o.total) > 100;

    
Only Lisbon qualifies: Ana’s three orders plus Chen’s come to 137.75.

  


  
Each customer’s single biggest order
    
See the window functions section; the answer depends on your database.

    
SELECT customer_id, id, total
FROM (
  SELECT o.*, row_number() OVER (PARTITION BY customer_id ORDER BY total DESC) AS rn
  FROM orders o
  WHERE customer_id IS NOT NULL
) x
WHERE rn = 1;

    
SELECT customer_id, id, total
FROM orders
WHERE customer_id IS NOT NULL
QUALIFY row_number() OVER (PARTITION BY customer_id ORDER BY total DESC) = 1;

  


  
Revenue by month
    
SELECT date_trunc('month', ordered_on) AS month, sum(total) AS revenue
FROM orders
GROUP BY 1
ORDER BY 1;

    
SELECT strftime('%Y-%m', ordered_on) AS month, sum(total) AS revenue
FROM orders
GROUP BY 1
ORDER BY 1;

    
GROUP BY 1 means “the first SELECT column”. Handy for quick queries, fragile in long-lived code.

  


  
A running total of revenue across all orders, by date
    
SELECT ordered_on, total,
       sum(total) OVER (ORDER BY ordered_on, id) AS running_revenue
FROM orders
ORDER BY ordered_on, id;

  


  
Orders whose customer doesn’t exist in the customers table
    
SELECT o.*
FROM orders o
LEFT JOIN customers c ON c.id = o.customer_id
WHERE c.id IS NULL;

    
This is the anti-join pattern written with LEFT JOIN. It finds order 15.
