System design field guide

Earn your complexity

Every box you add is something that can break at 3am, so start with one box and add each piece only when a real signal tells you to. Here’s what the pieces are, when each one pays for itself, and what it looks like on each kind of host.

      What you’re signing up for

      Costs are rough orders of magnitude for a modest workload, not quotes.

      Before you add any box, ask

      1. What exactly is slow or fragile? Measure it. “It might not scale” is not a signal; a p95 latency graph is.
      2. Would a bigger machine fix it? Vertical scaling is one setting change. A modern server with 32 cores and 128 GB of RAM is not exotic.
      3. Can the database you already have do it? Postgres can be your queue, your cache for many cases, your full-text search and your JSON store until you have proof otherwise.
      4. Who gets paged when it breaks? If the answer is “me, and I don’t know how it works,” wait.
      5. Can you take it back out? Prefer pieces that are easy to remove. A CDN is; a microservice split usually isn’t.

      Where to run it

      Same pieces, different names. Hosting is a translation layer: once you know what a load balancer or object storage does, each provider is mostly a catalog of their version of it. Hide columns to compare just the options you’re weighing.

      Stage 0 to 1, five ways

      The same small app (web app, Postgres, file uploads) set up on each kind of host.

      PaaS

      Connect the repo to Render or Railway, add their Postgres, store uploads in R2 or S3. Point DNS at it. Done in an hour; you never SSH anywhere.

      VPS

      One Hetzner or DigitalOcean box, Docker Compose or Kamal for the app, Caddy for HTTPS, Postgres in a container with nightly backups to a B2 or R2 bucket.

      Cloudflare

      Worker for the app, D1 or an outside Postgres through Hyperdrive, R2 for uploads. Strong fit if your app works as short request handlers.

      Google Cloud

      Cloud Run for the container, Cloud SQL for Postgres, Cloud Storage for uploads. Probably the gentlest of the three big clouds.

      AWS

      ECS on Fargate behind an Application Load Balancer, RDS Postgres, S3. More setup (VPC, IAM, security groups), but it’s the most common stack on job listings. Lightsail is the simpler on-ramp.

      Shipping it

      CI/CD is how code gets from your laptop to production safely and repeatably. It follows the same rule as the architecture: start with a script, and add machinery when a missed step or a bad deploy tells you to.

      One trip through a pipeline

      1. Commit and push

        Small changes, often. A pull request is where review happens.

      2. Check

        Lint, type-check, run tests. Keep it under ten minutes or people stop waiting for it.

      3. Build

        Build one artifact, usually a container image, tagged with the commit SHA.

      4. Store

        Push it to a registry. The exact same image goes to staging and to production.

      5. Migrate

        Run database migrations that the old code can still live with.

      6. Deploy

        Swap old for new: recreate, rolling, blue-green or canary.

      7. Verify

        Health checks, a smoke test, and a glance at the error rate.

      8. Roll back

        Redeploy the previous image tag. Practice it before you need it.

      Earn your pipeline

      1. A deploy script. ./deploy.sh that connects over SSH, pulls, migrates and restarts. Perfectly fine for one person.

        Move on whenyou forget a step, or someone else needs to deploy.

      2. CI on every push. GitHub Actions or GitLab CI runs the tests on each pull request. It’s free for most small projects, so do this almost immediately.

        Move on whenyou trust the tests enough to let a green build ship.

      3. Continuous deployment. Merging to main builds an image and ships it. Rollback means redeploying the previous tag.

        Move on whenreviewers need to click through changes, or config mistakes keep reaching production.

      4. Staging or preview environments. One shared staging copy, or a temporary environment per pull request (PaaS hosts make this nearly free).

        Move on whenyou couldn’t rebuild production from scratch in an afternoon.

      5. Infrastructure as code. Servers, DNS, buckets and permissions defined in OpenTofu, Terraform or Pulumi, reviewed like any other code.

        Move on whenbad deploys are expensive and you have enough traffic that 1% of it tells you something.

      6. Progressive delivery. Canary releases, feature flags, automatic rollback on error spikes. Ship code switched off, then turn it on for a slice of users.

        This is the top rungfor most companies. Beyond it is platform engineering.

      Migrations without downtime

      During a deploy, old and new code run at the same time, so every migration must work with both. Use the expand-and-contract pattern:

      1. Add the new column or table (expand).
      2. Deploy code that writes to both old and new.
      3. Backfill existing rows.
      4. Deploy code that reads from the new one.
      5. In a later deploy, drop the old one (contract).

      Never rename or drop something in the same deploy as the code that stops using it.

      A realistic small-team pipeline

      GitHub Actions tests every push to main, builds an image, pushes it to GitHub’s registry, and tells a VPS running Docker Compose to pull and restart. That’s rungs one through three.

      # .github/workflows/ship.yml
name: ship
on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

  build-and-deploy:
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          # image names must be lowercase on ghcr.io
          tags: ghcr.io/your-org/your-app:${{ github.sha }}
      - uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: deploy
          key: ${{ secrets.DEPLOY_SSH_KEY }}
          script: |
            cd /srv/app
            export IMAGE_TAG=${{ github.sha }}
            docker compose pull
            docker compose run --rm app npm run migrate
            docker compose up -d
            docker image prune -f
